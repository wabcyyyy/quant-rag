# doc-rag · 企业文档 RAG

[![CI](https://github.com/wabcyyyy/quant-rag/actions/workflows/ci.yml/badge.svg)](https://github.com/wabcyyyy/quant-rag/actions/workflows/ci.yml)

面向公司会议记录类文档（**飞书/Word 批量导出后手动迁入的 PDF / .doc(x)**，1121 篇 / 3856 块）的检索问答系统。
设计决策、取舍理由与评估口径见 [docs/design/PLAN.md](docs/design/PLAN.md)；**现行系统设计（架构手册）**见 [docs/architecture/system-design.md](docs/architecture/system-design.md)；文档索引见 [docs/README.md](docs/README.md)。

## 架构

文字摘要如下；**改代码前的现行链路说明**见 [docs/architecture/system-design.md](docs/architecture/system-design.md)；
完整流程图见 [docs/architecture/diagrams/](docs/architecture/diagrams/)；架构总览见
[docs/architecture/ARCHITECTURE.md](docs/architecture/ARCHITECTURE.md)。

```text
┌────────────────────────────────────────────────────────────────┐
│                 CLI（typer）  /  FastAPI /query                 │
└──────────────────────────────┬─────────────────────────────────┘
                               │
┌──────────────────────────────▼─────────────────────────────────┐
│  Orchestrator（唯一装配点，四条问答路径共用）                     │
│    → QueryRewriter（LLM 改写）→ HybridRetriever                 │
│    → Reranker → max_contexts 截断 → Synthesizer（引用+拒答）     │
└──────────┬─────────────────────────────────┬───────────────────┘
     在线 │ 每题                            │ 离线 │ 一次
┌─────────▼─────────────┐   ┌───────────────▼──────────────────┐
│ Embed(BGE-M3 dense)   │   │ PDF(PyMuPDF+碎化行重建+find_tables)│
│ + BM25(qdrant 内置，   │   │ docx(LibreOffice→mammoth 保标题)  │
│   jieba 预分词)        │   │  （导出后手动迁入 data/raw）        │
│ → 查询向量化           │   │  → 统一中间 JSON（blocks+页码）    │
│ → 双路 prefetch        │   │  → 结构感知分块（表格整块不切）     │
│ → RRF 融合（服务端）    │   │  → 元数据（文件名正则+LLM 可选）    │
│ → 元数据过滤+空结果回退 │   │  → Embed → Qdrant upsert         │
│ → 重排取 6 块          │   └───────────────┬──────────────────┘
└─────────┬─────────────┘                   │
┌─────────▼─────────────────────────────────▼──────────────────┐
│   Qdrant（dense + bm25 双索引 · payload index） · .env 密钥     │
│   LLM：DeepSeek deepseek-flash（合成与 RAGAS judge 同源）       │
└───────────────────────────────────────────────────────────────┘
```

设计要点（完整理由见 [PLAN §2/§3](docs/design/PLAN.md)）：

- **自研薄编排，不引编排框架**：重型轮子全用库（Qdrant/BGE/PyMuPDF/RAGAS），定制层自己写。
  编排只有 `src/doc_rag/orchestrator.py` 一处：CLI / FastAPI 两个端点 / Gradio 演示页 / eval
  五条入口共用它，`tests/test_orchestrator_parity.py` 把这五条入口（含 CLI 的默认与
  `--stream` 两种形态）各驱动一次，断言送进 LLM 的 prompt 逐字相同、重排调用次数相同、
  上下文块数相同。
  此前这条链在 6 处内联重复并已经漂移——服务端点漏掉重排与上下文截断，头条数字描述的是
  一条没有交付入口在跑的管线。
- **默认 Hybrid**：纯 Dense 搞不定文号、专名、精确条款（消融 #1）。RRF 由 Qdrant 服务端实现，
  平滑常数不可配（配置里不留 `rrf_k` 这种没人读的键）。
- **检索块 ≠ 合成块**：小块召回、`min(max_contexts, rerank.top_n)` 决定进 LLM 的块数。
  检索指标在**未截断**清单上算、LLM 只看截断后那份，两份清单不合并（合并会静默改掉
  Hit@k/MRR/nDCG 的分母）。重排**只重排序、不截断**——它以前兼做清单截断，于是
  「有重排」臂在 6 条清单上算指标、对照臂在 8 条上算，两臂不可比（见消融 #3 重测）。
- **检索指标的名字就叫 Hit，不叫 Recall**：`hit_at_5/8/清单末` 量的是「gold 来源文档的
  首个命中在前 k 位」；「找全没有」是 `mean_doc_coverage`（逐条真 Recall 的 macro 均值），
  并且必须和它自己的结构上限 `coverage_ceiling_mean` 一起读——清单 8 格而某题 gold 有
  56 篇时，那道题的覆盖率上限就是 0.143，与 0.96 不是一回事。
- **引用可追溯**：答案 `[n]` → `（文档名 第p页）` → Qdrant payload 的 doc/page/block。
- **评估驱动，先验证度量本身**：judge 上下文与 LLM 逐字一致、抽样均匀覆盖、
  小于噪声地板的差异不下结论（**Faithfulness 的地板：v1·55 条实测 1.4pt，v2·64 条重判同一批
  答案实测 1.87pt → 现行取 ≥1.9pt**）、延迟必须关缓存测、改写结果随条目落盘供重放复现、
  重排失败不许结果文件继续自称 `+rerank`；结果文件还要自证**清单长度**（`list_len`）、
  **过滤被放弃了几条**（`filter_fallback_n`）与**检索预算口径**（`budget: fixed:8 / rewrite`），
  否则「A 臂比 B 臂好」随时可能只是两条臂跑的配置不同。多臂 × 多指标的对照一律过
  **Holm–Bonferroni** 校正（`compare-ragas` / `compare-retrieval`）——12 个配对检验里
  挑一个 p<0.05 出来，和单次检验不是一回事。

## 快速开始

```bash
cp .env.example .env   # 填 Key：LLM=DeepSeek 官方 / Embedding=SiliconFlow
uv sync                # 安装依赖，首次生成 uv.lock（版本随之锁定）
docker compose up -d   # Qdrant :6333（镜像在 compose 里钉 v1.19.1，不是 latest）
uv run doc-rag check   # 冒烟：LLM 连通 / Embedding 维度与 dense_dim 一致 / sparse 探测 / Qdrant 版本与钉版一致
uv run doc-rag profile # Phase 0：语料画像（data/raw 放入语料后执行）
uv run doc-rag ingest  # 双路接入 → data/parsed 统一中间 JSON
uv run pytest          # 测试（206 项，全离线 mock，零 API 成本；CI 跑 ruff check + ruff format --check + mypy + pytest）
uv run doc-rag check-rewrite  # 查询改写泛化门禁（真实调用模型，会花约 ¥0.01，并打印生效模型与逐次延迟）
```

> `check` 排在 `compose up` **之后**是有意的：它现在把 Qdrant 也当冒烟对象
> （连不上即 exit 1，版本与钉版不一致也 exit 1）。顺序反过来，照抄的人会在第一步
> 就撞到「[Qdrant] 连不上」。

## 示例语料（clone 即可端到端体验）

真实语料不入库；`data/sample_raw/` 附带一套**虚构公司「云帆科技」的合成会议纪要**
（10 篇 PDF，由 `scripts/make_sample_corpus.py` 确定性生成，内容与黄金集样例
`golden_sample.json` 的 doc_id 互相咬合）：

```bash
uv run doc-rag ingest  --raw-dir data/sample_raw --parsed-dir data/sample_parsed \
                       --kb doc_rag_sample --recreate
uv run doc-rag eval    --kb doc_rag_sample --gold data/eval/golden_sample.json \
                       --rewrite --rerank --fresh-answers
uv run --extra demo doc-rag demo --kb doc_rag_sample   # 演示页连示例库
```

实测（10 条全真实调用，成本 ≈¥0.02）：Hit@k/MRR/nDCG、包含匹配、拒答、引用全部 1.0，
端到端 p95 ≈4~5s。注意：**10 篇小库满分只背书「管线正确、eval 判分口径可跑通」**，
真实语料上的难度与结论看下方黄金集 v2 各节；`--parsed-dir` 让示例解析产物与公司语料
目录隔离，避免把全量中间 JSON 误灌进示例 collection。

## 双路接入（统一中间表示）

PDF 与 docx 归一到同一套 block 模型，下游分块/入库只认它，不认来源。语料为飞书/Word 批量导出后**手动迁入 `data/raw`**，项目不对接平台 API：

```jsonc
// data/parsed/<doc>.json（示意内容，字段名与 src/doc_rag/ingest/schema.py 一致）
{
  "meta": { "source_type": "pdf", "doc_id": "…", "title": "会议档案_办公会_2026年第42周-会议纪要" },
  "blocks": [
    { "type": "heading", "heading_level": 1, "text": "二、议题讨论" },
    { "type": "paragraph", "text": "……", "page": 3 },          // page/bbox 仅 PDF 来源携带
    { "type": "table", "text": "| 项目 | 金额 |……", "page": 3 }  // find_tables 重建，整块不切
  ]
}
```

- **碎化 PDF**（飞书导出 4.5% 文档文本层「每字符一行」）：按纵向间距合并相邻行修复，
  逐字 grounding 校验违规 30/44 → 0。
- **带框表格**：`find_tables` 重建为单个 table 块——结构感知分块的表格完整率 **100%** vs 固定 512 切 **52.5%**。

## 评估结果（黄金集 v1 · 63 条 7 题型 · 1121 篇语料；v2 已扩至 72 条见 PLAN §5.3）

> **命名更正（2026-09-19）**：本节 2026-09-19 之前写作的 `Recall@k` 一律改称 `Hit@k`——
> 口径与数字都没变（`first_hit_rank ≤ k` 的条目占比），变的是名字：它从来不是
> 「检回多少比例的 gold」。64 条可答题里 44 条只有 1 篇 gold，其余 20 条 gold 有
> 10~56 篇，所以在 8 个槽位上真 Recall 的均值上限只有 0.79（`coverage_ceiling_mean`），
> 0.945 这种数只可能来自命中率。历史表格里的旧名保留，读的时候按 Hit 理解。

**消融 #1 检索**（纯 Dense vs Hybrid，top-8）：

| 指标 | 纯 Dense | Hybrid（默认） |
|------|---------|---------------|
| Recall@5 | 0.836 | **0.909** |
| Recall@8 | 0.891 | **0.945** |
| MRR | 0.764 | **0.794** |

增益集中在精确匹配类题型（decision 0.75→0.88 · term 0.75→0.83 · time_filter 0.80→1.00）。

**消融 #2 分块**（固定 512 切 vs 结构感知）与 **#3 重排**（无 → 有）：

| 对照 | 检索指标 | 机制/代价 |
|------|---------|----------|
| 固定 512 vs 结构感知 | 固定 512 反而略优（Recall@8 0.982 vs 0.945——块更细命中概率更高） | 结构感知表格完整率 **100% vs 52.5%**；修正口径下 Faithfulness **无差异**（0.5pt < 1.4pt 噪声地板）→ 结构感知的价值在**表格完整性与元数据**，不在召回 |
| 无重排 vs 有重排（v2 口径 72 条，nDCG 新增） | rewrite 恒定：MRR 0.804→**0.842** · Recall@5 0.891→**0.922** · **nDCG@8 0.808→0.810（≈持平）** | 榜首精度换上下文长度：重排把 top-6 削给 LLM，nDCG 数到的第 7/8 位被裁掉——增益在榜首，不在列表级。**⚠ 这行的前提已失效**：当时「rewrite」是 8 条中文子串规则，见下方重测 |

**消融 #3 重排（2026-09-19 在 LLM 改写下重测；同日两次修正，见下）**：

第一版重测（13:52，72 条 · top-8 · 仅检索侧）给出的是这张表：

| 指标 | 无重排 | 有重排 | 差 |
|------|--------|--------|-----|
| Hit@5 | 0.8906 | **0.9219** | **+3.1pt** |
| Hit@8 | 0.9219 | 0.9219 | 0 |
| MRR | **0.8326** | 0.8242 | −0.8pt |
| nDCG@8 | **0.8301** | 0.7965 | **−3.4pt** |
| 文档覆盖率 | **0.7233** | 0.7069 | −1.6pt |

> **但这张表 itself 有口径缺陷，且缺陷就在「+rerank」那一列**：当时重排器把检索清单
> 顺手砍到 `rerank.top_n`=6，而 `retrieved`（那份号称未截断的清单）就是它的返回值——
> 于是有重排臂的 nDCG@8 / 覆盖率是在 **6 条**清单上算的、对照臂在 **8 条**上算。
> −3.4pt 与 −1.6pt 里有多少是排序质量、有多少只是「清单短了两格」，这张表答不了。

第二版（同日 19:2x，重排改成「只重排序、不截断」，两臂同为 8 条；进 LLM 的仍是 6 块）：

| 指标 | 无重排 | 有重排（等长清单） | 差 | 第一版报的差 |
|------|--------|------------------|-----|-------------|
| Hit@5 | 0.8906 | **0.9219** | **+3.1pt** | +3.1pt |
| Hit@8 | 0.9219 | 0.9219 | 0 | 0 |
| MRR | **0.8326** | 0.8242 | −0.8pt | −0.8pt |
| nDCG@8 | 0.8303 | 0.8299 | **−0.04pt（无差异）** | −3.4pt |
| 文档覆盖率 | 0.7233 | 0.7233 | **0（无差异）** | −1.6pt |

> **结论改写**：清单等长之后，nDCG@8 与文档覆盖率的两处「重排的代价」全部归零——
> 它们本来就是清单长度的函数。重排真正买到的只有 **Hit@5 +3.1pt**（把该进 top-5 的
> gold 提进 top-5），真正付出的只有 **MRR −0.8pt**。两个数都落在 64 条可答题的
> 2~3 题之间，所以这条开关的净效应仍在噪声边缘：留着它的理由是「上下文只送 6 块时
> 榜首更干净」，不是「列表级排序更好」。
>
> 顺带量到一条服务侧事实：**同配置连跑两遍（改写 100% 命中缓存），72 条里 8 条
> （11%）的 top-6 上下文集合不同**（不是顺序不同），而 Hit@5 / nDCG@8 / 覆盖率
> 两遍逐字相同。也就是说重排在 **6/7 边界上不是位级可复现的**——同一句话问两次，
> 一成情况下 LLM 看到的不是同一批块。任何小于几个百分点的检索侧差异都别归因给模块。
> 复现：`doc-rag eval --gold data/eval/gold.json --kb doc_rag_demo --rewrite [--rerank] --retrieval-only`

第三版（同日深夜）把这套判读**工具化**了：`doc-rag compare-retrieval` 用 RAGAS 轨同一套
机器跑检索轨——同题配对差 + 自助法 95%CI + 符号检验 + **Holm 多重比较校正**（家族 =
本次运行的全部比较，指标 × 臂，所以对照臂必须一次跑齐），并把「两臂清单不等长 /
覆盖率上限不等」直接标成伪影。跑出来的是：

| 对照 | 结论 |
|------|------|
| 有重排 − 无重排（等长 8 格） | 四个指标**全都不能与「无差异」区分**：Hit@5 +3.1pt 是 2 题翻正 / 0 题翻负（赢/输/平 2/0/62，p=0.50，95%CI 下界正好 0）· Hit@8 0 · MRR −0.8pt（p=0.79）· nDCG@8 −0.04pt（p=0.82） |
| 检索轨重跑噪声 | **doc 级指标为 0**：同配置两遍，64 条可答题的 Hit@5/Hit@8/MRR/nDCG@8/覆盖率逐条全等（配对判读 0/0/64） |

> **所以「重排真正买到的只有 Hit@5 +3.1pt」这句也要收回**：n=64 时 1 题就是 1.56pt，
> 这个样本量下 ≤2 题的差在统计上不可能显著。等长口径下的正确说法是**重排对检索指标
> 无可测影响**；留着它的理由只剩「上下文只送 6 块时榜首更干净」，而那句还没被单独量过。
> 上面那条 11% 的不确定则完全落在「哪 6 块进 LLM」这一层——其中只有 4/72 条换了
> **文档**，另 4 条换的是同一篇文档的另一个**块**。也就是说检索指标可以放心当
> 确定性量用，而**答案侧的 run-to-run 差异不会有任何检索指标先报警**。

**生产预算下聚合题检索到什么程度**（`--honor-rewrite-budget`，聚合题按
`retrieval.aggregate_top_n`=25 取池、两路 prefetch 50；`eval` 默认固定 top_n=8 是为了让
各消融臂同预算可比，代价是以前从没量过生产口径）：

| 指标 | 固定 top-8 | 生产预算（聚合题 25） | 该清单长度下的上限 |
|------|-----------|---------------------|------------------|
| 文档覆盖率（全量） | 0.7233 | **0.8325** | 0.9445 |
| cross_doc 覆盖率 | 0.2086 | **0.5018** | 0.7272 |
| time_filter 覆盖率 | 0.3020 | **0.6888** | 0.8857 |
| nDCG@8 | 0.8299 | 0.8399 | — |

> **注意这条改进没进 LLM**：三臂的 `contexts` 都恒为 **6 块**（`rerank.top_n`），
> 所以放宽检索预算只改善了「检回来多少」，聚合答案看到的仍是 6 块里的 6 篇。
> 要把覆盖率的提升兑换成答案质量，得动上下文预算——那会作废现有全部质量基线，
> 目前没有动（见「已知不足」）。
>
> **而且那 +10.9pt 几乎全是「清单变长」**（8 格 → 平均 13.25 格，上限 0.7917→0.9445）。
> 用同口径的 `coverage_vs_ceiling`（拿到的 gold 篇数 / 这份清单本可以拿到的篇数）重读：
> 0.8906 → **0.8723**（−1.8pt，赢/输/平 4/10/50，p=0.18 不显著），cross_doc 更是
> 0.8125 → 0.6877。→ 相对预算的**捕获率没有提升**，涨的是格子数。于是「上下文预算
> 消融」的性质也变了：它不再是「检索变好了、去看答案」，而是「纯粹多喂几篇文档进
> prompt 值不值」——一个成本与噪声的决策，不再是检索质量决策。

**消融 #4 引用约束**（30 条同题对照）：引用存在率 **0.067 → 1.00**，且顺带提升包含匹配
+6.7pt（要求标注来源促使模型贴原文而非自由改写）。

**消融 #5 元数据过滤**（时间限定聚合题）：文档覆盖率 **0.61 → 0.96**（实体聚焦查询 +
宽检索预算 + 过滤，三者缺一不可；普通事实题加过滤会误伤——doc_date 仅覆盖 ~19% 语料）。

> **前提修正（2026-09-19）**：「实体聚焦查询」当时是 8 条中文子串规则，实测只在黄金集
> 自己的措辞上触发（样例集 10 条命中 2 条，命中的恰好是 cross_doc 与 time_filter 那两行；
> 7 条同义改写 0 命中）。所以 0.96 这个数是在**规则触发条件 == 评测集措辞**下测出来的，
> 不可迁移。改写已换成 LLM，并改由一条独立的泛化门禁量（下表）；0.61→0.96 保留为
> 「过滤本身有效」的证据，不再作为端到端能力主张。

**查询改写泛化门禁**（`doc-rag check-rewrite`，30 条同义改写 · 真实调用 deepseek-flash）：

| 指标 | 数值 | 门禁 |
|------|------|------|
| 聚合意图 recall | **0.95**（19/20） | ≥0.80 ✓ |
| 年份过滤命中 | **10/10** | — |
| 单点题误触发率 | **0.10**（1/10） | ≤0.10 ✓ |
| 改写退化（不可解析/调用失败） | 0 | =0 ✓ |

两条已知误判留在门禁里而不是改标签：`异地灾备机房选址的整个经过` 判成单点（措辞确实没
露枚举意图）；`公司在区块链存证方面有什么制度或布局？` 判成聚合（边界题，「有什么制度或
布局」本身就是枚举句式）。

> **门禁集本身去过污染（2026-09-19 晚）**：上表第一次测的时候，30 条里有 4 条是被改写
> prompt 的 few-shot 例子教过的——`fact-02`「新仓库计划什么时候投入使用？」与 `fact-03`
> 「公司对采购审批权限做出了什么调整？」和示例输入**逐字相同**，`aggyear-01` 与第三个
> 示例只差几个字，`aggyear-07` 与它相似度 0.60。这正好是我们作废消融 #5 用的那条判据
> （「触发条件 == 评测集措辞」），所以它必须量到自己。4 条已换成未被教过的措辞，
> **换完重跑数字不变**（0.95 / 10-10 / 0.10，两条已知误判仍是那两条，4 条新题走真实调用
> p50 831ms）→ 这个 0.95 不是抄来的。防复发：`tests/test_rewrite_llm.py` 断言门禁题与
> few-shot 输入的归一化相似度必须 <0.6。
> 下面「换更小改写模型」那张对照表的 recall / 误触发列测于换题之前，方向性结论
> （更慢、误触发翻倍）不受影响，但要引用具体数字得在新题集上重跑。

**换更小改写模型的实测结论（2026-09-19）：不换。** 改写调用本身 p50 **632~817ms**
（4 轮各 n=30 · 关思考 · 关缓存），它就是检索侧从 ~420ms 升到 ~1.3s 的主要增量。
同一套 30 条门禁题、同条件换模型实测：

| 改写模型 | p50 | p95 | recall | 单点题误触发 |
|----------|-----|-----|--------|-------------|
| deepseek-flash（现网） | **643ms** | 1.02s | 0.95 | **0.10** |
| Qwen3-30B-A3B-Instruct-2507 | 1010ms | 3.21s | 1.00 | 0.20 |
| Qwen2.5-7B-Instruct | 755ms | 1.93s | 1.00 | 0.20 |
| Qwen3.5-4B | 21~46s / 次 | — | — | — |

更小 ≠ 更快：两个 SiliconFlow 候选延迟是现网的 1.2~1.6 倍、误触发翻倍；4B 档无视
`reasoning_effort=none`（照样思考）。DeepSeek 官方也没有比 flash 更小的档（只多一个
更大的 v4-pro）。提示词瘦身同样没换来东西：去掉输出里的 `reason`（30.6 → 19.1 输出
token）后延迟变化落在轮间抖动内（p50 594~694ms），所以**保留 `reason`**——它是人工
核对判定依据的唯一把手。真正拿到的是**尾部收敛**：改写现在带自己的预算
（`rewrite.timeout_s: 5` + `max_attempts: 2`，最坏 5+2+5=12s），此前继承合成侧的
180s × 4 次重试 ≈ 最坏 12 分钟；超时退化为「不改写」并被计数（`check-rewrite` 打印
退化数，`eval` 落 `meta.rewrite_degraded`，全退化直接中止）。同一问题重复问命中响应
缓存，改写零成本。

**Faithfulness 的低分条目归因（`doc-rag probe-judge`）**

先记一条 15 条抽样臂的结论（同一条答案、temperature=0、关缓存连判三次 = **0.167 / 1.0 /
0.167**）：q029 那道五门课的枚举题被判 0.167，judge 的理由却是「上下文列出了包含《X》的
五门课」——RAGAS 把枚举拆成 5 条「五门课程是《X》」的单门陈述，判定阶段按**排他**读，
5 条一起判否。内容在，被罚的是拆句后的措辞。

全量 72 条这轮的最低四条，逐个 probe：

| 条目 | 分 | 归因 |
|------|----|------|
| q014（term） | 存 0.00 → 复判 **0.50** | 拆句把答案揉成「议程和目标提到朱彦真」这种不通顺的单句，再判它推不出来。**同一答案两次判分不同** |
| q040（open_discussion） | 0.40 | 答案主体是「文档没记录这次讨论的结论」的正确指出；判否的是拒答套话 + 两条带「只」的排他陈述 |
| q003（decision） | 存 0.43 → 复判 **1.00** | 七条陈述复判全 ✓。又是一次块级翻转 |
| q063 / q064（time_filter） | 0.67 | 两条都是**正确拒答**：实质陈述判 ✓，唯一判 ✗ 的是「根据现有文档无法回答该问题」——那一句断言的是问答情形，按构造不可验证 |

**口径结论**：单题 Faithfulness 在**枚举 / 拒答 / hedge** 这三种形态上不可复现（本轮两条
0 附近的分复判都翻了），条目级幅度远大于 §「评估可信度」里 n=55 均值的 1.4pt 噪声地板。
所以 Faithfulness 只在两种用法上可信：**同规模配对比**（`doc-rag compare-ragas`）与
**大样本均值**。绝对值前后对比一律先 `probe-judge` 再下结论；本轮 0.9264 里的低分没有一条
被证实是真正的不忠实答案。

| 题型 | 端到端 p50 | 端到端 p95 | 答案均长 |
|------|-----------|-----------|---------|
| cross_doc（聚合 · 已关思考） | 3.2s | 3.7s ✓ | 537 字 |
| time_filter（聚合 · 已关思考） | 3.0s | 6.2s ✗ | 637 字 |
| fact | 3.9s | 9.7s | 86 字 |
| term | 3.5s | **39.5s** | 62 字 |
| decision | 5.0s | 18.1s | 224 字 |
| open_discussion | 6.7s | 18.9s | 300 字 |

> 每类 n=8~12，最近秩法下这一列的 p95 **就是该类的最大值**——别读成「95% 的请求都这么慢」。
> 聚合类 p50 3.0~3.2s，说明尾部是单条而不是普遍水平。

> **P95 ≤ 8s 目标不达标（分流前的旧状态，2026-09-18）**：端到端 p95 32.8s，33%（21/63）的条目超 8s。根因是
> deepseek-flash 的输出里 **91% 是看不见的 reasoning token**，聚合题要跨 15～25 块归纳，
> 思考量随之爆炸。**压延迟的唯一有效杠杆是关掉合成侧思考**（`DOC_RAG_LLM_REASONING_EFFORT=none`）：
> p95 32.8s → **2.6s（达标）**、成本 −94%，代价是包含匹配 −10.9pt（p=0.031）、
> Faithfulness −6.4pt（p=0.0015）。
>
> **但分题型看，聚合题关思考是免费的**：包含匹配 1.00→1.00、Faithfulness 反而 0.936→0.979，
> 延迟却从 24～32s 降到 2s。**已启用分流**（`DOC_RAG_LLM_REASONING_EFFORT_AGGREGATE=none`，
> 2026-09-18 拍板）：聚合题关思考、其余保思考——实测聚合题端到端均值 **27.7s → 2.7s（10.3×）**、
> max 3.7s，13/13 包含匹配不变、Faithfulness 0.961/0.967（噪声内）。延迟目标相应改写为
> **分题型 SLO**（聚合 ≤5s ✓ / 短答 ≤8s——短答题的思考尾部是已拍板的质量取舍）。
> 复现：`uv run doc-rag eval --rewrite --rerank --fresh-answers`（`--fresh-answers` 必须加——
> 缓存命中的毫秒数是本地查询耗时，不是模型延迟）。

> **分流后的现状（2026-09-19 全量 72 条）**：超 8s 的条目 **21/63 → 11/72**（33% → 15.3%）。
> 聚合侧 p50 3.0~3.2s 已进 SLO 量级，p95（=该类最慢一条）cross_doc 3.7s ✓、
> time_filter **6.2s ✗ 略超 5s**。剩下的尾部全部在**非聚合题**：`term` 的 p95 就是单条最慢的
> **39.5s**（q034：8,425 个输出 token 里 8,332 是看不见的思考，只为一条 140 字的答案），
> decision 18.1s、open_discussion 18.9s。短答侧 ≤8s **不达标**，且它是已拍板的质量取舍
> （全关思考包含匹配 −10.9pt）——要收这条尾巴得给非聚合题也加思考预算上限，
> 那要重新量质量代价才能动。

> **Faithfulness 的 0.77 是度量 bug，已修正**：judge 拿到的上下文缺了 `（文档名 第p页）` 前缀，
> 而合成 prompt 要求标注来源文档名 → 答案里「《某文档》中…」被判为不忠实
> （提及文档名的 18 条均值 0.475，不提的 37 条 0.716）。把 LLM 实际看到的上下文原样交给 judge 后，
> 同一批答案从 0.6375 升到 **0.9563**，消融 #2 的 18pt 假差距随之归零（修正后 0.5pt，
> 小于 1.4pt 的 judge 噪声地板）。复盘见 PLAN §5.3。
> 配套：RAGAS 抽样改为**均匀覆盖**（原先取前 N 条，整段漏掉排在末尾的 cross_doc/time_filter）；
> 逐条分数落盘；`doc-rag compare-ragas` 出配对差 + 95%CI + 符号检验 + 噪声地板，
> 检索轨同套判读走 `doc-rag compare-retrieval`（外加 Holm 多重比较校正与
> 「两臂清单是否等长」护栏）；
> `doc-rag probe-judge` 打印单条的 judge 中间产物（口径 bug 就是靠它定位的）。

> **延迟数字曾是笔糊涂账**：PLAN 里同时存在「端到端 ≈6.3s 达标」与「deepseek-flash 1.3s」
> 两个矛盾的数——前者测于另一个模型且是估算，后者是无上下文的连通性 ping。根因是
> **仓库里没有任何延迟测量代码**。现在 `eval` 落盘分阶段 + 分题型分位数，结果文件 `meta`
> 自证 `llm_model` / `answer_cache` / `prompt_fingerprint`。

## 已知不足与下一步

- **Faithfulness 的单题分值不可复现**：枚举拆句、正确拒答的套话、以及 prompt 要求写出的
  「文档没记载…」hedge 这三种形态都会被系统性扣错分（见上文「低分条目归因」：q014 复判
  0.00→0.50、q003 复判 0.43→1.00）。**没有绕过**——绕过要改 RAGAS 的拆句/判定提示词，
  等于换度量身份。所以：0.9264（n=64）只能与同规模、同黄金集版本比，绝对值前后对比一律先
  `probe-judge`；比较一律走 `doc-rag compare-ragas` 的配对差。
- **包含匹配 0.875 → 0.8438（−3.1pt ≈ 2 题）尚未归因**：检索侧同条件下几乎没动
  （Hit@5 都是 0.922），所以不像改写造成的，但要知道是不是噪声，得补一条
  「同 72 条 · 改写开/关」的对照（约 ¥0.25）。在补之前这 3.1pt 记为「未解释」，
  既不声称退步也不声称持平。
- **改写上了关键路径，「换小模型」这根杠杆已用完**：这次调用实测 p50 632~817ms，是检索侧
  ~1.3s 的主要增量。换更小/更近的模型已量化否决（见「泛化门禁」节的对照表：更慢且误触发
  翻倍），提示词瘦身的收益落在轮间抖动内。尾部已用 `timeout_s/max_attempts` 封住。
  剩下的可能只有两条：改写与首路检索并行发起（代价是一次可能浪费的检索），或换本地小分类器
  （代价是多一个推理依赖）。当前都不做。
- **元数据过滤仍只有一个字段能用**：`doc_date` 覆盖 211/1121 篇（18.8%），
  `topics` / `attendees` 在默认入库下全库为空（0/3856），因此不再为其建索引、
  也不再在文档里宣称可按其过滤——要用得显式 `ingest --llm-meta`。
- **引用可追溯受页码覆盖率限制**：`page` 只落在 2717/3856 块（70.5%，docx 来源普遍没有页码）；
  且跨页块继承首块页码，多页块的引用页号可能偏早。
- **延迟目标已改为分题型 SLO，只达标一半**（2026-09-19 全量 72 条）：聚合侧 p50 3.0~3.2s，
  p95（=该类最慢一条）cross_doc 3.7s ✓ / time_filter 6.2s **✗ 略超 5s**；短答侧 ≤8s ✗——
  超 8s 的条目从 33%（21/63）降到 15.3%（11/72），但 `term` 单条最慢 **39.5s**
  （8,332 个思考 token 只为 140 字答案）。归因已闭环：合成耗时与思考 token 逐条相关
  **0.996**，慢条目（>8s）平均思考 5,389 token（快条目 498）。收这条尾巴要给非聚合题也加
  思考预算，代价需重新量（全关思考包含匹配 −10.9pt）。
- **Answer Relevancy 0.39**：复测+人工归因（2026-09-18）确认不是中文噪声——指标把
  正确拒答与忠实的「未决」表述判为 noncommittal 记 0 分（open_discussion 题型整体 0.00），
  仅适合作诊断信号，不进质量门禁。
- **黄金集 time_filter 弱点已补**：v2 口径 12 条（答案集上限 15→40，覆盖率与 v1 不可直接比）。
- **聚合题是本项目最大的未完成项，而且现在有了准确的数**：生产预算（聚合题取 25 块）
  下 cross_doc 文档覆盖率 **0.5018**、time_filter **0.6888**，各自上限 0.7272 / 0.8857；
  默认固定 top-8 时只有 0.2086 / 0.3020。**但这两档都没进 LLM**——`rerank.top_n`=6
  让三条臂的上下文恒为 6 块，所以「检回来更多」目前不兑换成「答得更好」。
  而且按同口径的 `coverage_vs_ceiling` 读，放宽预算的捕获率其实是 0.8906→0.8723
  （不显著）——涨的是格子数，不是找得准。**下一步不是 GraphRAG 而是先做一次上下文预算
  消融（6 → 15/25 块，聚合题 20 条）**，但它的性质已经明确：纯粹「多喂几篇文档进
  prompt 值不值」的成本/噪声决策，不再是检索质量决策（输入 token 与延迟都要重测，
  现有聚合题质量基线全部作废）。
- **重排在 6/7 边界上不是位级可复现的**：同配置连跑两遍（改写 100% 命中缓存），
  72 条里 **8 条（11%）的 top-6 上下文集合不同**，而汇总指标两遍逐字相同。
  现在这条有了准确的刻度：其中只有 **4/72 换了文档**、另 4 条换的是同一篇文档的另一个块，
  而 **doc 级检索指标逐条全等**（`compare-retrieval` 的配对判读 0/0/64 → 重跑噪声地板 = 0）。
  也就是说：检索指标是确定性的，**答案侧的 run-to-run 差异不会有任何检索指标先报警**；
  单题级别「这次答得比上次差」只能靠 `ragas_from_results` 的重放自检
  （上下文对不上就拒判）拦住，根因就在这里。
- **拒答审计过了跨供应商这一关，但「一致」不等于「正确」**：同一批落盘答案 + 同一份落盘
  上下文 + 同一个 prompt，只换判分方（deepseek-flash 同源 vs SiliconFlow Qwen3-30B-A3B），
  v2/v1 两批各 8 条**零翻转**（都是 0/8 编造）；而正对照——往一条拒答里注入一句「2026 年
  3 月通过每吨 120 元碳税决议」——**两家都判「有编造」并逐字回引**，所以这个 0 不是两家
  一起放水。剩下那层偏袒排不掉：两个模型共享的训练偏好可能让它们以同一种方式宽容。
  Faithfulness 也已跨供应商重判（0.9451 vs 0.9700，配对差 p=0.185 不显著），结论同样不变。
  **真正没被排除的是「两个 judge 一起宽松」这种可能**——正对照只能证明它们抓得住明显注入。
- **judge 的地板比之前记的大**：同一批答案、同一个 judge、temperature=0，全量 n=64 重判
  一次差 **1.87pt**（0.9264 → 0.9451）。以前引用的是 v1·n=55 那两轮的 1.4pt。所以
  **落在 1.4~1.9pt 之间的 Faithfulness 差值不再有结论资格**（消融 #2 的 0.5pt 无差异仍安全）。
  另一条一起学到的：`eval.judge.timeout_s` 原本 60s，跨供应商那轮在 8 并发下掐断了
  最长上下文的条目（**time_filter 12 条里丢了 6 条**），缺的全是难条目，均值被幸存者抬到
  0.9726（补齐后 0.9700）。已提到 180s，并记下「LLM 判分的缺失要看题型分布」。
- **幽灵块现在会被报出来，但还没在真实库上清过**：`doc_id` 是源文件 sha256[:16]，
  删文件**或改一个字节**都会让旧点变成孤儿（改名不会——内容寻址）。它们不会被任何
  ingest 覆盖，而**照样能被检索命中**，带的是旧日期与旧正文。现在每次 `ingest` 结束都
  做反向对账并打印幽灵篇数/块数，`ingest --prune` 只报告、`--prune --yes` 才删
  （三道闸：有解析产物读不通、要删的比留下的多、`--limit` 时判据降级）。
  代价是这还没跑过真实语料（要 Qdrant）：**当前基线库里语料之外的点数是未知数**，
  而且清过之后检索基线必须重跑才能继续引用现有数字。
- **~15 份真扫描件**（聊天截图/扫描合同）未走 MinerU 兜底；图片 caption 未入库。
- notebooks（接入对比 / 消融可视化）未做。
- 全部结论可复现：复现命令逐条见 [PLAN §6](docs/design/PLAN.md)；commit 历史按决策粒度提交。

## 注意

- `data/raw`、`data/parsed`、`data/eval` 已 gitignore——**公司文档严禁提交**（合规，见 docs/design/PLAN.md §8；
  两个例外都是脱敏合成样例：`data/eval/golden_sample.json` 见「评估集可复现性」，
  `data/eval/rewrite_paraphrase.json` 是查询改写的泛化门禁集，内容全部指向示例语料）
- `docs/ops/`、`docs/personal/` 不入库；工程文档见 `docs/architecture/`、`docs/design/`、`docs/guides/`（见 [docs/README.md](docs/README.md)）
- **`.cache/llm_cache.sqlite` 里是问题原文 + 检索到的文档正文**（缓存键带完整 prompt，
  命中即返回）。它让重复评估近乎零成本，但也是两件事：① 语料内容在磁盘上的一份副本，
  ② re-ingest 之后还能命中旧答案。所以有 `doc-rag cache-stats`（条数/体积/按模型分布）
  与 `doc-rag cache-clear --yes`（作废），`doc-rag ingest` 结束时主动报还剩多少条。
- API Key 全部走环境变量（`configs/default.yaml` 中 `env:` 前缀）
- **`doc-rag serve` 需要 `DOC_RAG_API_TOKEN`**：未配置时 `/query` 与 `/query/stream`
  一律 503 拒绝服务（fail-closed），`/health` 保持免鉴权供探针使用。`kb` 参数只能在
  `api.allowed_collections` 白名单内取值，并限流（`api.rate_limit_rpm`，默认 30/分钟——
  窗口按**服务端那一个令牌**聚合，所以现在等价于全局配额而不是按调用方分；要多租户限流
  得先有多身份。慢请求可占住线程池槽位到 180s，没闸门就是自我 DoS；多 worker/多实例下
  每份进程各算各的，那要换共享存储）。日志只落结构化度量，
  **不含问题原文与文档正文**。`GET /metrics`（同样要令牌）出请求数 / 分阶段 p50、p95 /
  重排与改写失败计数 / 过滤回退次数 / 流式断连计数。
  **CORS 有意不开**：这是带令牌的知识库接口，浏览器直连只会把令牌摊进前端；
  要 Web 界面就走同源反向代理，或用 Gradio 演示页。
- 评估依赖：`uv sync --extra eval`
