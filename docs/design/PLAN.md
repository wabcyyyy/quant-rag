## 1. 项目定位

**问题**：几百份分散的会议记录里没有可靠的检索与复用路径。「关于供应商预付款，我们做过哪些决定」这类问题，全文搜索答不了，参与过会的人也记不全——而「哪一次会定了什么」正是这类语料唯一的价值所在。

**难在语料同质**：一个查询动辄命中几十份结构相似的记录，区分靠的是会议身份（日期/参会人/议题）与决议状态，而不是单纯的语义相似度。另一条硬约束是**「讨论过但未决定」不能答成已决**——由合成 prompt 的规则约束 + 专项评估题守住，不靠模型自觉。

**因此工程预算花在四处**：入库时的结构元数据抽取、Dense+BM25 混合检索 + 元数据过滤 + 重排、强制引用与无据拒答、以及自建黄金集驱动的消融评估。接入层刻意做薄（见 §2「不做的事」）。

## 2. 技术决策（已确认）

| 项 | 选择 | 理由 |
|----|------|------|
| 路线 | 自研薄编排层：重型轮子全用库，公司定制层自己写 | 不重复造轮子；贡献集中在文档特有定制，讲得清 |
| 接入 | 飞书/Word 批量导出 PDF + doc(x)，手动迁入 data/raw | 不对接平台 API；增量靠重下 + sha256 去重 |
| 文件解析 | doc/docx：LibreOffice headless + mammoth；PDF：PyMuPDF | born-digital 语料，轻依赖即可；MinerU 仅在画像发现扫描件时兜底 |
| 元数据抽取 | LLM 入库时抽取：日期、会议类型、参会人、议题、决议 | 会议记录的检索价值一半在元数据；300 份短文档抽取成本可忽略 |
| 编排 | 自研 Pipeline（不引编排框架，模块边界清晰） | 解析/分块/评估全是深度定制，框架抽象碍事；agent 一期同样拍板自研薄循环，见 §5.5 F2 |
| 存储 | Qdrant（Dense + 全文 BM25 双路） | Query API 原生 RRF 融合；单存储，几千份规模无压力 |
| Embedding | BGE-M3 dense via SiliconFlow API | 中文文档正确默认；API 不吐 sparse（2026-09 查证），hybrid 第二路走 Qdrant full-text BM25 |
| Reranker | bge-reranker（本地小模型）或 API rerank | 性价比高 |
| LLM | DeepSeek 官方 API：`deepseek-flash`（实测选定，见「模型选型」） | 包含匹配 0.836 vs GLM-4.5-Air 0.745，价差被本地响应缓存抵消；思考型模型，合成侧延迟是主要瓶颈 |
| 评估 | RAGAS + exact-match 双轨；黄金集 v0 ≥30 → 终版 ≥50（v1 实为 63 条，题型分布见 §5.3） | LLM 打分与确定性指标互为校验 |
| 交付 | CLI + FastAPI；Gradio 演示页作加分项 | 基线优先，演示够用即可 |

**不做的事（刻意收窄，避免烂尾）**：多租户权限、生产 K8s、GraphRAG 全量、多模态 VLM 深度集成（可留作 roadmap）。

```text
└───────────────────────────────┬─────────────────────────────────┘
                                │

└───────┬───────────────────────────────┬─────────────────────────┘
        │ 在线                          │ 离线
┌───────▼───────────────┐     ┌─────────▼─────────────────────────┐
│  Hybrid Retriever     │     │  Ingest Pipeline                  │
│  Dense+BM25+RRF      │     │  多源→归一化→分块→LLM元数据→Embed→入库│
│  → Rerank → top-n     │     │  doc(x) · PDF(PyMuPDF) · 手动迁入 raw     │
└───────┬───────────────┘     └─────────┬─────────────────────────┘
        │                               │
┌───────▼───────────────────────────────▼─────────────────────────┐
│   Qdrant（向量+全文） · SQLite/JSON 元数据 · data/raw 原文件         │
└───────────────────────────────┬─────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────┐
│  OpenAI 兼容 LLM API · BGE-M3（Dense+Sparse）· bge-reranker（本地/API）│
└─────────────────────────────────────────────────────────────────┘
```

**五条设计原则**

1. **接入克制**：born-digital 简单版面快通道已够，不为想象中的难例引重依赖——MinerU 是条件触发；语料手动迁入，不对接平台 API。  
2. **检索块 ≠ 合成块**：小块/句级召回，父块/窗口进 LLM。  
3. **默认 Hybrid**：纯 Dense 搞不定条款号、文号、专名，Dense+BM25 双路是底线。  
4. **引用可追溯**：答案 → `[1][2]` → `doc/page/block`。  
5. **评估驱动**：改任何参数先跑黄金集，拒绝「感觉变好」。

## 5. 核心实现要点

### 5.1 离线 Ingest

```text
PDF（飞书/Word 批量导出，手动迁入 raw）→ PyMuPDF：文本块 + find_tables 重建带框表格
doc/docx            → LibreOffice headless 归一 → mammoth（保留标题结构）
    → 统一中间 JSON（blocks: type/heading_level/text；PDF 附 page/bbox）
    → 结构感知分块
    → 元数据（doc 级 LLM 抽取：date/meeting_type/attendees/topics/decisions +
      chunk 级：title, section_path, page, block_type）
    → Embedding
    → Qdrant upsert + 元数据落盘
```

元数据以 LLM 抽取为主；文件名日期（会议纪要命名惯例）用正则解析作第二信号交叉校验；增量靠重下 + sha256 去重（几千份内无压力）。

**幂等与对账：两个方向都要量**

`doc_id = sha256(源文件)[:16]`（内容寻址），所以「增量」只有两种形态：新增文件、内容改过的文件——**改名不产生新 doc_id**。入库按 doc_id 删旧再插，于是有两个方向的差额：

- **正向（解析 → 入库）**：差额逐项有归属（空文档 / 解析失败 / `limit` 截断）。改造前
  1127 篇只入库 1121 篇，那 6 篇空文档在任何输出里都不存在。
- **反向（库 → 语料）**：删旧只删「本次要重插的那篇」。所以**源文件被删掉或改过内容时，
  旧 doc_id 的点永久留在库里，而且照样能被检索命中**——带的是旧日期与旧正文。改一份纪要
  = 新 doc_id，新旧两份同时在库里被召回。这比漏入库更难发现：没人会怀疑结果里有它。
  它同时是「哪一次会定了什么」这类时效/版本题的前置缺陷（旧决议被后续会议推翻时，
  被推翻的那份还在被引用）。

现在每次 ingest 结束都做反向对账：全库 scroll 一遍只取 `doc_id` payload
（3856 块 ≈ 4 次请求），报幽灵文档数与块数、「语料有库里没有」的篇数、以及 parsed_dir
里已无对应源文件的陈旧产物。`ingest --prune` **只报告**，`--prune --yes` 才删，删前三道闸：
① 有解析产物读不通 → 拒绝（那些旧点归属无法判定）；② 要删的比留下的多 → 拒绝（几乎一定是
`--kb` 或 `--parsed-dir` 串了库）；③ `--limit` 时 `keep` 判据自动从「本次源文件」退回
parsed_dir（子集不能当全集判据）。

> ⚠ 本项**尚未在真实库上跑过**（需要 Qdrant）：当前基线库里到底有多少点是本次语料之外的，
> 仍然是未知数。清过幽灵块之后检索基线要重跑才能继续引用现有数字。

**分块默认**

| 规则 | 值 |
|------|-----|
| 正文块 | 300–600 汉字 / ~400–800 tokens，overlap 10–15% |
| 切分依据 | 会议记录按议题/发言人段落优先；通用走标题层级 → 段落 → 滑动窗口 |
| 表格/公式 | 整块，禁止硬切 |
| 必带元数据 | `doc_id, page, section_path, block_type` |

Qdrant 侧为 `doc_id / page / block_type` 建 payload index，支撑元数据过滤与规模化检索。

### 5.2 在线 Query

```text
问题 → (可选)改写/关键词 + 实体/时间识别
     →（可选）元数据过滤（date / attendee / topic）
     → Dense top-k + BM25 top-k（Qdrant full-text，jieba 预分词）
     → RRF 融合 (k=60)
     → Rerank 取 5–8 块
     → 扩父块 / 去重
     → LLM：仅依据上下文 + 编号引用 + 不足则拒答
```

> Phase 1 正选：BM25 为 hybrid 第二路（已查证：SiliconFlow API 不返回 sparse 权重，2026-09）。learned sparse（火山引擎 BGE-M3 / 本地 GPU FlagEmbedding）列为 Phase 2 消融实验。

> 跨文档聚合题（「关于 X 我们做过哪些决定」）：检索结果按 doc_id 聚合去重后再合成，引用按文档归组。

### 5.3 评估闭环

黄金集 **终版 ≥ 50 条**（v1 63 条；**v2 现 72 条**：v0 从 30 起步），类型覆盖：

> **v1 分布（63 条 = 55 可答 + 8 无答案）**：fact 12 · term 12 · open_discussion 10 ·
> decision 8 · cross_doc 8 · no_answer 8 · time_filter 5。
> ⚠️ 此前 §2 写的「每题型 ≥8」**未达成**：time_filter 只有 5 条，其 p95 延迟与
> 覆盖率数字都建立在 n=5 上（p95 基本等于 max）。**这是 v1 的已知弱点**。
>
> **v2（2026-09-18 夜，全程序化构造、零 LLM 生成）**：fact 12 · term 12 ·
> open_discussion 10 · **decision 10**（8 LLM 原题 + 2 决议区程序化构造）·
> cross_doc 8 · no_answer 8 · **time_filter 12**（答案集上限 15→40、每年 ≤6 条）。
> v1 冻结于 `gold_v1.json`（旧数字可追溯）；v2 直接替换 `gold.json`，
> **题目 id 已重排——文中 q007 等历史引用一律为 v1 口径**。
> 注意：time_filter 答案集变宽后其覆盖率与 v1 不可直接比较。
> 程序化决议题质量从严（决议线索词白名单 + 未决措辞/评估类排除，全库候选仅 2 条通过），
> v2 全量评估中 2 条均答对（first_hit_rank 1/2、包含匹配 ✓）。

- 单会事实题（某次会上说了/定了什么）  
- 决议确认题（讨论过但未决定——决议/讨论区分，faithfulness 专项）  
- 时间/参会人限定题（测元数据过滤增益）  
- 跨文档聚合题（「关于 X 我们做过哪些决定」）  
- 术语/文号/编号题（测 Sparse/BM25 价值）  
- 少量表格数值题（预算表等）  
- **无答案题**（未讨论过的议题，测拒答）  

| 指标 | 目标（示例） | 实测（见「指标达成情况」） |
|------|----------------|--------------------------|
| Context Recall@10 | ≥ 0.80 | **0.964** ✓ |
| Faithfulness | ≥ 0.85 | **0.95** ✓ |
| Answer Relevancy | ≥ 0.80 | 0.40（judge 中文噪声，待重判） |
| 事实题 exact-match（日期/数值/文号类） | ≥ 0.85 | 0.8545（包含匹配口径） |
| 无答案拒答率 | ≥ 0.90 | **1.00** ✓ |
| P95 延迟 | ≤ 8s | **32.8s ✗**（开思考；关思考 2.6s 达标但质量 −10.9pt） |

**必须能展示的对比实验（简历数字来源）**

1. 纯 Dense vs Dense+BM25 vs Dense+Sparse（Recall@10，三组）  
2. 固定 512 切 vs 结构感知分块（Faithfulness）  
3. 无 Rerank vs 有 Rerank（MRR / nDCG）  
4. 无引用约束 vs 强制引用（人审 Citation Accuracy）
5. 无元数据过滤 vs 有元数据过滤（时间/参会人限定题 Recall）

**已跑出的结果（黄金集 v1 · 63 条 · 1121 篇语料）**

消融 #1 纯 Dense vs Hybrid（Dense+BM25+RRF，top-8）：

| 指标 | 纯 Dense | Hybrid | Δ |
|------|---------|--------|---|
| Recall@5 | 0.836 | **0.909** | +7.3pt |
| Recall@8 | 0.891 | **0.945** | +5.5pt |
| MRR | 0.764 | **0.794** | +3.0pt |

分题型（Recall@8）：fact 1.00→1.00 · open_discussion 1.00→1.00 · decision 0.75→0.88 ·
term 0.75→0.83 · time_filter 0.80→1.00 · cross_doc 1.00→1.00
→ Hybrid 增益集中在精确匹配类（decision / term / time_filter）。

**跨文档聚合题：度量修正与预算规律**

- **度量陷阱**：来源集合曾只取 `@姓名：` 提及的文档（黄日航 8 篇 vs 全库 **205 篇**含名），
  把正确检索判为未命中。修正为「全部含名文档」后 Recall 类指标对聚合题失去区分度
  → 改用**文档覆盖率**（检索到的来源文档数 / 答案集大小）。
- **覆盖率上限 = top_n / 答案集大小**：康少云（56 篇）top-8 上限 0.14，实测 0.12 已达上限 84%。
- **预算扫描**（聚合检索，按文档去重）：cross_doc 0.13（top-8）→ 0.22（top-15）→ 0.35（top-30）；
  time_filter 0.37 → 0.68 → 0.82。
- **实体聚焦查询**（剥离「公司文档里出现过哪些讨论或安排」模板话术，只用人名检索）：
  周碧玉 0.06→0.22、何李健 0.10→0.21。

消融 #5 元数据过滤（时间限定题 · 实体查询 + top-15 聚合）：

| 指标 | 无过滤 | 年份过滤 | Δ |
|------|-------|---------|-----|
| 平均文档覆盖率 | 0.61 | **0.96** | +35pt |

→ 结论：**聚合题的正确形态 = 实体聚焦查询 + 宽检索预算 + 元数据过滤**，三者缺一不可；
这也解释了为什么单纯换融合策略（Dense↔Hybrid）对聚合题无效。

**元数据稀疏性：过滤前必须看字段覆盖率（教训）**

- `doc_date` 在本语料仅覆盖 **18.7% 文档**（125 篇文件名 + 86 篇正文抽取）：
  会议档案 114/384 有完整日期（其余用周次 `2025年第44周`），工作/议事档案几乎无日期。
- 后果：对普通事实题加年份过滤会误伤 80% 语料，实测 **fact 覆盖率 1.00→0.33**、
  Recall@5 0.909→0.564。
- 对策两条：① 日期过滤只在明确时间限定的聚合题上启用；② `retrieve` 加空结果回退
  （过滤后结果 < 3 条则去掉过滤重试）。
- 修复后产品路径（改写开）：Recall@5 0.909 · Recall@8 0.945 · MRR 0.836 ·
  覆盖率 0.799；time_filter 覆盖率 0.357→0.657，cross_doc 0.121→0.209。

**产品化落地**：`QueryRewriter`（规则实现，零 LLM 成本）识别聚合意图/实体/年份 →
`doc-rag query` 与 `/api/query` 自动应用；`backfill` 命令支持元数据规则演进后
**原地更新 payload（不重新向量化）**。
> ⚠️ 本段的「规则实现」已于 2026-09-19 作废：8 条子串规则只在黄金集自己的措辞上触发，
> 换成了 `LLMQueryRewriter`（一次模型调用，独立泛化门禁），见 §5.4 W3。
> `backfill` 的原地更新 payload 不变。

**消融 #2 固定 512 切 vs 结构感知分块（检索指标）**

| 指标 | 固定 512 切 | 结构感知分块 |
|------|------------|-------------|
| 块数 | 5541 | 3856 |
| Recall@5 | 0.909 | 0.909 |
| Recall@8 | **0.982** | 0.945 |
| MRR | **0.804** | 0.785 |
| 文档覆盖率 | **0.796** | 0.759 |
| 分题型（decision/term） | 1.00 / 0.92 | 0.88 / 0.83 |

**表格完整性（机制验证，免费可测）**

| 分块策略 | 表格完整率 |
|---------|-----------|
| 固定 512 切 | **52.5%**（85/179 个表格被切断或跨块） |
| 结构感知 | **100%**（表格整块不切） |

→ **反直觉结论**：检索指标反而偏向固定切分（块更多更细 → 命中概率更高）。
结构感知分块的价值不在召回，而在**表格完整性与章节上下文**（近半数表格被硬切后，
LLM 会读到断裂的表格行）。这印证了 PLAN 把这组消融的度量定为 **Faithfulness** 是对的——
**选错度量会得出相反结论**。Faithfulness 对比见下（同 judge 下重跑）。

**消融 #2 Faithfulness 全量复测：一次度量口径 bug 的完整复盘**

先核对口径：原记录的 0.641 / 0.821 一度被当成「15 条抽样值」（配置里 `ragas_sample: 15`），
但查 judge 缓存发现原始判分已覆盖全部 55 条可答题（112 次陈述抽取调用 ≈ 2 分支 × 55 + 重试），
**原值本就是全量**。用全量 55 条独立重跑复现，差异 ≤0.35pt：

| 分块策略 | 原记录（旧口径） | 独立重跑（旧口径） | 修正口径 |
|---------|---------------|-----------------|---------|
| 结构感知（默认） | 0.641 | 0.6375 | 0.9563 / 0.9423（两轮，均值 0.9493） |
| 固定 512 切 | 0.821 | 0.8210 | 0.9546 |
| 配对差异（固定 − 结构） | +0.180 | +0.1834（95%CI +0.070~+0.297，p=0.014） | +0.0054（95%CI −0.030~+0.041，p=0.46） |

**这 18pt 既不是抽样造成，也不是 judge 噪声**：独立重跑与原值差 ≤0.35pt；而 18pt 是噪声地板
（1.4pt，见下）的 13 倍，符号检验 p=0.014（赢/输 30/13），是个统计上稳固的差异。
但它**不是分块策略的质量差异**——追下去发现是**评估口径 bug**：

- 送 LLM 的上下文带 `[n]（文档名 第p页）` 定位前缀，而存进结果文件、再喂给 RAGAS 的
  上下文**只有正文**。合成 prompt 要求答案标注来源文档名，于是「《某文档》中…」这类
  归属陈述在 judge 眼里无据可依，整条被判为不忠实。
- 量化：结构感知分支里提及文档名的 18 条均值 **0.475**，不提的 37 条 **0.716**（24pt 全在口径上）；
  固定切分分支提及的 10 条 0.854，反而略高于不提的 0.814。
- 两个分支受罚程度不同，是因为**固定 512 切的块正文自带文档标题**（硬切不剥标题行），
  judge 能在正文里找到；结构感知把标题放进元数据（section_path），正文里没有。
  同一条答案在两个分支的「可验证性」不同——**分块策略被意外耦合进了度量口径**。
- 最典型的一条 q007：答案逐字引用上下文里的「最小规格（2核CPU，1G内存，0副本）：67元/月」，
  judge 判 0.00，理由是「上下文没有提到《高校排名网站运维服务报价单》这一文档标题」。
  **逐字引用被判成不忠实**，7 条零分里 5 条属此类。

修正：把 LLM 实际看到的上下文串（含编号与文档名前缀）原样交给 judge；上下文带 `[n]` 编号后，
答案里的引用标记也从「永远无法验证的陈述」变成可验证项。修正后 18pt 差距归零
（配对差 +0.5pt，95%CI 跨零，p=0.46），分题型差异也全部落在 5pt 内。

**judge 噪声地板（同条件全量重跑两轮，关 judge 缓存）**：0.9563 / 0.9423 →
**均值的噪声地板 = 1.4pt**；55 条里 **21 条（38%）分数会变**，多数在 ±0.06 内，少数 0.16~0.32
（如 q019 0.88→0.56）。注意：15 条子集两轮只差 0.7pt，**小样本会低估噪声**——条目级翻转
不会按 √n 均掉，噪声地板必须用与结论同规模的全量来测。
→ 修正口径下 0.5pt 的差距**小于噪声地板，判为无差异**；旧口径的 18pt 是噪声地板的 13 倍，
是稳固差异，但来源是口径 bug。

**残余噪声的机制（单条 0↔1 翻转的原因）**：抽查 q007——答案逐字引用上下文原文，
修正口径下两轮里有一轮给 1.0，单独再跑一次却给 0.00，理由是「上下文没有提到『数据库本体』」。
而「数据库本体」只出现在**问题**里，不在答案里：**陈述抽取器把问题措辞注入了陈述**，
NLI 再据此判否。这是修正口径后残留的主要噪声源。
定位手段已固化为 `doc-rag probe-judge <结果文件> <条目id>`（打印抽出的陈述 + 逐条判定 + 理由）。

**检索侧的不可复现性（附带发现）**：同配置重跑，重排 API 对近似并列项会抖动——
63 条里有 3 条（结构感知）/ 14 条（固定 512）的上下文发生变化（合成缓存命中率 95% / 78%），
包含匹配随之在 0.800~0.818 间波动。**重排不是位级可复现的**，这比 judge 温度更值得注意：
它同时污染检索指标与答案，且两次重放的块**集合**都会变（不只是顺序）。

**延迟口径（与 §5.3「评估可信度口径」并列）**

- **缓存命中的耗时不是延迟**：命中时只查一次本地 sqlite（毫秒级）。测延迟必须
  `--fresh-answers`（或 `DOC_RAG_LLM_CACHE=0`）；结果文件里 `latency.cache_contaminated`
  为真就说明本轮合成延迟被低估。
- **数字必须能追到出处**：结果文件 `meta` 记录 `llm_model` 与 `answer_cache`，
  `summary.latency` 记录分阶段与分题型分位数。此前延迟数字只存在于 PLAN 文本里，
  没有脚本也没有结果文件，才导致两个数互相矛盾而无人察觉。
- **分题型报，不报单一值**：本语料延迟双峰，混合 P95 会同时低估短答案、藏起聚合题。
- **样本量决定 p95 的可信度**：n<20 时 p95 基本等于 max。`_quantiles` 用最近秩法
  （不做插值），小样本下更保守。
- **检索侧与 LLM 解耦**：检索延迟只依赖嵌入 + Qdrant + 重排，换模型不必重测。

**模型选型（2026-09 实测，黄金集真实题目含拒答陷阱）**

> ⚠️ 「延迟」列的来源：除 deepseek-flash 一行外，其余各值取自 `doc-rag check` 的
> **连通性 ping**（无上下文、无 system prompt 的单句请求，约 20:13 及之前测得），
> 用途仅是**同口径横向排序**（谁比谁慢一个数量级一目了然），**不是合成延迟**，
> 不可与「延迟实测」一节的分位数混用。deepseek-flash 一行的 1.3s 即来自该 ping，

**成本控制（与供应商无关，最有效）**

- **judge 关思考（`eval.judge.reasoning_effort: none`）**：输出 token −90%，同模型不动 judge 身份
- 换模型省的钱不如砍调用量：一轮完整评估 ≈ 62 次合成 + 50 次 judge
- DeepSeek 官方有错峰折扣（北京时间 00:30–08:30），批量评估可挂夜间

**成本审计与优化（Phase 2，实测 token 数）**

调用量盘点（优化前）：

| 环节 | 调用量 | 单次用量 | 问题 |
|------|--------|---------|------|
| 文档元数据抽取 | **1 次/文档 = 1130 次** | ~2–3k 输入 | 最大单点；date 靠正则即可，topics/attendees 未被任何检索路径使用 |
| RAGAS judge | 25 条 × 2 指标 × 多次内部调用 ≈ 100–200 次 | 含上下文 | 第二大；AnswerRelevancy 中文噪声大（0.40 但答案明显切题） |
| 合成问答（评估） | 62 次/轮 | 普通题 2646 输入；**聚合题 6911 输入 + 1471 输出** | 7 条聚合题占整轮 25% 输入 / 48% 输出 |
| **响应缓存** | **完全没有** | — | 同批 62 条题重复跑了 6 轮（372 次调用，约 310 次是重复付费） |

已实施的四项优化：

1. **本地响应缓存**（`llm.cache`，`.cache/llm_cache.sqlite`）：键 = 模型+messages+参数哈希，
   命中即返回不发请求。实测重复评估命中率 **76%**（48/63），**同配置重跑基本零成本**；
   换模型/prompt 自然产生新键，不会误用旧答案。可用 `DOC_RAG_LLM_CACHE=0` 关闭。
2. **元数据抽取改 opt-in**（`--llm-meta`，默认关）：避免 1130 次调用的地雷。
3. **RAGAS 抽样 15 + 只留 Faithfulness**（`eval.ragas_sample` / `eval.ragas_metrics`）：
   judge 调用减少约 60%。
4. **上下文上限**（`retrieval.max_contexts: 10`）：约束输入 token；重排后通常更少。
   另删除配置里未实现的 `judge.repeat: 2`（避免配置说谎）。
5. **judge 调用量实测可见**（`_TokenCounter` 回调 + `--fresh-judge` / `--ragas-out`）：
   一轮全量判分 = 55 条 × **2 次调用** = 110 次，输入 18.7 万 / 输出 57.5 万 tokens。
   Faithfulness 每条约 2 次调用（抽陈述 + 一次**批量** NLI 判定），
   不是「每条陈述一次」——按后者估会高一个数量级。**先量再算。**
6. **逐条分数落盘**（`<结果文件>_ragas.json`，含 `per_item` / `by_type` / `token_usage`）：
   此前只打印到控制台，导致 PLAN 里的 Faithfulness 无法追溯到逐条分数，
   也就无法回答「差异是抽样、judge 噪声，还是口径 bug」——正是这次复测卡住的地方。

**成本审计第二课：账单的大头是「看不见的思考」，不是调用次数（2026-09-17 深挖）**

上面那批优化省的全是**调用次数**；把 9-17 全天账单拆开才发现方向没对准：

| 计费项 | token | 占比 |
|--------|-------|------|
| 输出（含隐藏 reasoning） | 6,259,669 | **74%** |
| 输入（未命中缓存） | 1,051,880 | 13% |
| 输入（命中缓存） | 1,099,877 | 13% |

- **deepseek-flash 是推理型模型**：judge 的输出里 **97~98% 是看不见的 reasoning token**
  （实测一次陈述抽取：可见 111 字符，计费 1,665 token，其中 1,609 是思考）。
  此前的成本审计按「可见文本长度」估输出（1471 token/条），**漏掉了 reasoning，低估一个数量级**。
- 最反直觉的结构：**「把答案拆成陈述」这个最简单的子任务最贵**（输出 1,700~1,900 token、可见仅百来字），
  是真正做判定的 NLI 步骤的 3~4 倍。
- **修复不需要换模型**：`reasoning_effort=none`（同一个 deepseek-flash、只关思考）
  → judge 输出 58.9 万 → **5.6 万 token（10.4×）**，reasoning 归零；
  Faithfulness 0.9460，落在开思考两轮（0.9563/0.9423）之间，配对差 −0.33pt（p=0.076），
  远在 1.4pt 噪声地板内。**一轮全量判分的成本从 ~¥5 降到 ~¥0.5**。
  合成路径暂不动（质量优先，且答案变体会使现有基线失效）——这是下一个可选实验。
- 输入侧的供应商 prompt cache 已在工作（实测单次 2,304/2,464 命中），不必再优化。

**成本护栏（配合「避免调度失误浪费」，全部有 mock 回归测试，零付费验证）**

7. **重试去重**：应用层 4 次 × SDK 默认 2 次 = 最多 12 次传输、RAGAS 默认再叠 10 次。
   现在 SDK `max_retries=0`、RAGAS `RunConfig(max_retries=2)`，且**只重试瞬时错误**
   （429/5xx/超时）；401/400 直接失败——对永久错误重试是纯浪费。
8. **缓存故障可见**：judge 缓存初始化失败会**直接报错拒绝跑**（静默降级 = 无缓存全量判分，
   实付 10 倍）；chat 缓存读写失败计数进 `cache_stats()`，评估结束打印可见。
9. **缓存键含 endpoint**：同名模型在 OpenRouter 与官方的答案不同，不能混用本地缓存。
   注：此改动使旧缓存全部失效，属一次性成本（reasoning 关闭后重灌很便宜）。
10. **temperature 入缓存键**：合成此前从未应用配置里的 temperature（走供应商默认）。
11. **入库默认安全**：`index_parsed` 的 `use_llm_meta` 缺省改读 `metadata_extraction.enabled`
    （默认 **false**）——此前库函数默认 `True`，任何程序化调用都会踩响 1130 次调用的地雷；
    `metadata_extraction.enabled` 也从死配置变成真开关。`--limit` 现在同时约束解析与入库
    （此前试跑照样全量嵌入）。
12. **抽样先于重检索**：`--ragas-from` 对旧格式文件补跑时，先抽样再为抽中的条目重检索
    （检索调 embedding、重排调远端 API，都不是免费的；旧实现会为 15 条抽样重放全部 55 条），
    并按 `meta.retrieval` 还原 dense/hybrid 模式（检索模式在构建 retriever 时就定死）。
13. **上下文不一致拒判**：重放后正文与存量对不上（rerank 非位级可复现所致）→
    **报错拒绝判分**，而不是拿替换后的上下文悄悄送进付费 judge——那是假数据加真花钱。
14. **计量补全**：`llm.chat` 此前完全没有 token 计量（合成侧是盲区）；现在与 judge 一致，
    输入/输出/**reasoning** 分列，评估结束打印「本次真实调用」。
15. **`--fresh-judge` 修通**：此前该开关只在 `--ragas-from` 路径生效，
    `eval --ragas --fresh-judge` 静默无效——想测方差时拿到的是缓存旧值，钱照付数据是假的。
    现在贯通全链路，且未启用 RAGAS 时直接报错退出。

**成本纪律（对齐「先算账再动手」）**：动手前给调用数与金额预估 → 有停止条件的小试跑
（`--limit` 现在真正生效）→ 一次只跑一个批处理 → 用落盘的 token 计量对账 →
差异小于 1.4pt 噪声地板不下结论。

**无答案题的构造教训（第三次黄金集迭代）**

- 词法校验不够：`公司关于差旅费标准的制度` 整句不存在，但语料有「差旅费由基础差旅和弹性差旅构成」
  → 题目实质可答（3/7 条因此不成立）。
- **词法校验也挡不住语义相邻**：`员工持股计划` 关键词不存在，但语料有 ESOP/股权激励内容；
  `岗位职级体系` 同理（语料有职级表）。
- 最终方案：主题改取**域外领域**（碳排放配额、ISO14001、对外担保额度、内幕信息管理、
  董监高责任保险等公司内部会议纪要不可能覆盖的题材）+ 关键词校验，8 条全部通过。
- 效果：拒答正确率恢复 **1.00**（此前 0.75 的"失败"里，部分是题目本身不成立）。

**消融 #2 固定 512 切 vs 结构感知分块（最终结论）**

| 指标 | 固定 512 切 | 结构感知分块 | 判读 |
|------|------------|-------------|------|
| 块数 | 5541 | 3856 | — |
| Recall@8 / MRR | **0.982 / 0.908** | 0.945 / 0.871 | 固定切分更优（块更细、命中概率更高） |
| 表格完整率 | 52.5%（85/179 被切断） | **100%** | 机制成立 |
| 包含匹配（63 条） | 0.818 | **0.836** | 差异在噪声内 |
| RAGAS Faithfulness（旧口径） | 0.821 | 0.637 | 实为度量口径 bug（见上节） |
| **RAGAS Faithfulness（修正口径）** | 0.9546 | 0.9493（两轮均值） | **无差异（0.5pt，小于 1.4pt 噪声地板）** |
| 表格相关题（11 条）包含匹配 | **0.909** | 0.818 | 机制未转化为收益 |

诊断（排除干扰解释）：
- 不是「答案越短越忠实」：两分支答案长度 303 vs 304 字、陈述数 7.0 vs 6.7 句，几乎一致；
  固定切分上下文反而更长（2664 vs 2342 字）。
- 不是「表格题没覆盖」：语料含表格文档 106 篇、来源含表格的题 11 条，专门对比后
  **固定切分在表格题上仍略优**（10/11 vs 9/11，样本小，属噪声）。

**诚实结论**：结构感知分块的价值（表格完整性）**在本语料与黄金集上未转化为可测质量收益**；
表格被切断的机制真实存在（47.5%），但片段仍常含所需数值，LLM 可据此作答。
**先前「固定切分忠实度更高 18pt」的结论已被推翻——那是度量口径 bug 而非质量差异**（见上节），
修正后两者无差异（0.5pt，小于 1.4pt 的 judge 噪声地板）。
→ 保留结构感知分块的理由变为「元数据与可解释性」（section_path、表格块类型可用于过滤与展示），
而**不是**已证实的质量提升。若要主张质量收益，需补表格数值型题目（当前黄金集缺该题型）。

**夜间开发记录（2026-09-18 凌晨，SPEC v1 执行 · 错峰窗口 · 实际总成本 ≈¥7.0 / 上限 ¥10）**

**Answer Relevancy 复测与归因改写（0.40 悬数字的结案）**

全量 55 条、judge 关思考、修正口径：**answer_relevancy = 0.3947**（trial 15 条 0.3456 → 全量
0.4556 波动内的收敛值；对照 judge 分题型：fact 0.71 / term 0.51 / cross_doc 0.40 /
time_filter 0.38 / decision 0.22 / open_discussion 0.00）。复测确认 0.40 不是抽样假象，
但 5 条人工抽查（打印 judge 反推问题 + 相似度）**推翻了「中文噪声大」的历史结论**：

- 5 条 0 分条目（q004/q005/q006/q012/q019）的**全部反推问题都被 judge 标记 noncommittal**，
  相似度被强制清零——而反推问题与原问题几乎逐字相同（若不清零，相似度本应接近 1）；
- 其中 q006/q019 是**正确拒答**（"根据现有文档无法回答"），q004/q005/q012 是忠实转述
  「讨论过但未决定」的谨慎回答——该题型的正确行为就是不给结论；

**判读工具化：`doc-rag compare-retrieval`（2026-09-19 深夜，把 RAGAS 轨那套搬到检索轨）**

`eval/compare.py` 的配对判读此前只服务 RAGAS 轨，检索轨的四臂对照一直是「比均值」。
现在检索轨共用同一套机器，逐条分数从结果文件的 `items[]` 派生（分母 = 有 gold 的 64 条，

三条结论：

1. **等长口径下重排对检索指标无可测影响**——包括此前当作唯一幸存结论的 Hit@5 +3.1pt。
   它是 2 题翻正、0 题翻负，n=64 时 1 题就是 1.56pt，这个样本量下 ≤2 题的差不可能显著。
   「能主张的只有 Hit@5 +3.1pt 与 MRR −0.8pt」这句要改成「四项全在功效之下」，
   留着重排的理由只剩「上下文只送 6 块时榜首更干净」，而那句还没被单独量过。
2. **生产预算的 +10.92pt 覆盖率几乎全是清单变长**（8 格 → 平均 13.25 格；上限
   0.7917→0.9445）。同口径的 `coverage_vs_ceiling` 反而从 0.8906 降到 0.8723
   （cross_doc 0.8125→0.6877），点估计向下、p=0.18。→ 「上下文预算消融」的性质变了：
   它不是「检索变好了去看答案」，而是「纯粹多喂几篇文档进 prompt 值不值」，
   一个成本/噪声问题。**E2 的决策代价因此比原来估的低**（不动检索质量的任何结论）。
3. **检索轨的重跑噪声地板 = 0（doc 级）**：同配置两遍，64 条的 Hit@5/Hit@8/MRR/nDCG@8/
   覆盖率**逐条全等**（配对判读 0/0/64）。上面第 3 条那 11% 的不确定全部落在
   「哪 6 块进 LLM」这一层，且其中只有 4/72 条换了**文档**、另 4 条换的是同一篇文档的
   另一个**块**。→ 检索指标可以放心当确定性量用；答案侧的 run-to-run 差异
   **不会有任何检索指标先报警**，只能靠上下文自检（`ragas_from_results`）挡。

落盘键随之改为 `answered_ok_subseq` / `contains_acc_subseq`（2026-09-19 之前的结果文件仍是
旧键名；没有代码消费它，只有人读）。理由是这路指标做的是**字符子序列**匹配——关键词的每个字
按序出现即命中，假阳性没有上界（「通过决议」能命中一句毫不相干的话，测试里锁了这个用例）。
原名听着像「容忍改写」，读数上又总与严格口径同值（本轮 0.8438 == 0.8438），等于一个看不见
自己在干什么的指标。收紧成词级匹配**没做**：在当前这批题上它与严格口径同值，也就还不知道
它想抓住什么——改名让语义可见，收紧与否留作能被讨论的决定。

**评估可信度口径（应对「RAGAS 是 LLM 打分，可信吗」）**

- **judge 的上下文必须与 LLM 实际看到的逐字一致**（含 `[n]（文档名 第p页）` 前缀）。
  这是踩过的坑：只传正文时，答案里凡提及来源文档名一律被判不忠实，两个分块分支因此产生
  18pt 的假差距（见「消融 #2 全量复测」）。**先验证度量本身，再比较数字。**
- judge 模型与版本固定，temperature=0；用 `--fresh-judge`（关 judge 缓存）+ `compare-ragas`
  实测运行间方差：同条件**全量 55 条**两轮差 1.4pt，55 条里 21 条（38%）分数会变；
  2026-09-19 又在 v2 全量 64 条上重判同一批答案，0.9264 → 0.9451 = **1.87pt** →
  **现行地板取 ≥1.9pt**（只有两次全量样本，只敢说「不小于」）。落在 1.4~1.9pt 之间的
  Faithfulness 差值从此不再有结论资格
  → **噪声地板要用与结论同规模的全量测**（15 条子集只差 0.7pt，会低估）
  → **小于噪声地板的差异不下结论**
- 抽样必须**均匀覆盖**，不能取前 N 条：黄金集按题型分块排序，`rows[:15]` 整段漏掉
  cross_doc/time_filter（同一批逐条分数换成前 15 条口径，差距会从 18pt 放大到 33pt）
- 配对判读三件事（`doc-rag compare-ragas --group 标签=文件1,文件2`）：
  ① 全量同题配对差 + 自助法 95%CI + 符号检验；② 组内重跑极差（噪声地板）；
  ③ 子集敏感性（同一批逐条分数，只换取样口径会得出什么结论）
- 只报告相对变化（before/after），不吹绝对分
- 人工抽查 15–20% 校准 judge
- 日期/数值/文号类事实题用 exact-match / 包含匹配，不依赖 judge

**黄金集构造的两次迭代（失败案例分析素材）**

- v0：跨文档题用词频选词 → 选出「处理结果/本处/case」等泛词与导出残留 token，
  来源集合无意义（Recall 0.25）。**根因是题目质量问题，不是检索问题。**
- v1：改为**结构信号抽人名**（`部门@姓名：` / 提案者 / 主持），并用 `@` 模式做交叉验证提纯
  → 18 个零噪声真人名，构造出有区分度的跨文档/时间题。零 LLM 成本（`gen-gold --programmatic-only`）。
- 同类问题：解析层碎化 PDF（每字符一行，4.5%）导致 grounding 校验 30/44 违规——修复行重建后归零。

1. `over_refusal_rate` 恒真：定义是「答案出现拒答措辞 且 上下文含关键信息」，而收紧后的
   prompt **要求**模型说明「文档里没记载什么」。本轮被标记的 26 条**全部**答对了
   must_contain → 0.406 是 100% 假阳性。已收紧为「且答案确实没交付关键信息」（本轮按新
   定义 = 0.0），两种情形各一条回归测试。一个恒真的指标比一个偏高的更糟——它会把人
   引去修一个不存在的问题。
2. Faithfulness 条目级不可复现：q014 存 0.00 → 复判 0.50，q003 存 0.43 → 复判 1.00，
   q029（15 条臂）同一答案三次判 0.167/1.0/0.167。机制是枚举答案被拆成排他单句、

**上面第 2 条的机制展开（15 条臂的 q029 / q063 · `probe-judge`）**：n=14 里两条离群值吃掉
0.092 缺口的 90%（q029 0.167 = 0.0595、q063 0.667 = 0.0238），两条都是度量侧：

- **枚举答案的块级翻转**（q029）：答案把五门课逐字列全并引用，上下文原文就是这五门；
  RAGAS 拆成 5 条「五门课程是《X》」的单门陈述后，判定阶段按排他读 → 5 条一起判否。
  **同一份答案、temperature=0、关缓存连判三次 = 0.167 / 1.0 / 0.167**，且 5 条同涨同落
  （一次批量调用决定整组，翻转相关而非逐条独立）。同题在 09-17 那轮（n=55）判 1.0。
- **拒答套话按构造不可验证**（q063，一条**正确**拒答）：两句实质陈述都判 ✓，
  唯一判 ✗ 的是「根据现有文档无法回答该问题」——它断言的是问答情形，不是文档内容。
  注意判分集合只排除 `type==no_answer`，`time_filter`/`fact` 上的正确拒答仍进集合并被扣。

### 5.5 Agentic RAG 升级（2026-09-20 拍板 · 方案与自评记录在 `docs/design/AGENTIC_RAG.md`）

一句话：在 `orchestrator` 之上加一层 **policy**（有界多步检索 + 证据自判），不引编排框架、
不做多轮会话、不动 §5.3 已经确立的单发基线口径。

下文「草案」= `docs/design/AGENTIC_RAG.md`，其 §N 编号是该文件内的编号。
**刻意不做**（草案 §2 的边界，一并搬过来）：不接外部工具与互联网、不做自由 tool 选择的
autonomous agent、不做多租户/权限、GraphRAG 全量仍留 Phase 3；**步数上限 ≤3**，单请求的
token 与延迟预算硬封顶。

**三条分叉的结论**

| 分叉 | 拍板 | 已接受的代价 | 重开条件 |
|---|---|---|---|
| F1 合成规则 3（禁止把多篇信息合并成任何单篇都不存在的陈述） | P1~P3 **一字不放宽**，「放宽」做成 P4 独立臂 | 第一版看起来「不够 agentic」，更像会自己多查几次的检索器，答案仍是逐篇事实的枚举 | 只由 P3 结论推动 |
| F2 循环自研 vs LangGraph / LlamaIndex workflows | **自研薄循环**（有界步数 + 显式状态 + trace 落盘），≈600 行 | 停机/重试/超时自己写；框架在 policy 与预算这两处本来就帮不上忙 | — |
| F3 多轮会话状态 | **本期不做**，agent 限定在「单条问题内的多步」 | 产品上少一个「追问」；换来不动服务契约（服务端状态要连鉴权、限流、缓存键、「同一句第二次问算不算同一测量」一起重做） | 独立一期 |

F1 的代价比草案写的**高一档**：草案把「放宽规则 3」和「agent 送了更多块进 LLM」混成一件事。
即使规则 3 一字不动，只要 agent 臂的 `contexts` 比单发臂多，faithfulness 就天然偏高。
**保住可比性的不是「不放宽」，而是答案轨的等长护栏** —— 它当时不存在，2026-09-20 已落地
（见本节末 P1-e；缺的一半是 P3 要真跑出一条同块数对照臂）。

**F2 的前置问题：为什么不是「确定性子查询分解器」**（草案 §9 第 5 条自己提出的更窄方案，不回答就不能定架构）

分解器与 agent 押的是同一条动机（§5.3：覆盖率被清单格数封顶 —— 8 格 0.7233 / 上限 0.7917，
生产预算 25 下 0.8325 / 上限 0.9445，而同口径 `coverage_vs_ceiling` 0.8906→0.8723，即变长
≠ 变准），成本与延迟确实更可预测，也**同样**需要 trace 与等长护栏。选 agent 的理由只有一条：
**分解器是 agent 的一个消融臂，反过来不成立。** 分解器 = 固定一步扇出、无证据自判、无停机决策；
agent 减去 `check_evidence` 再减去 `read_window` 就退化成它。所以做完 agent 能一次回答「收益
来自哪一步」，先做分解器则永远回答不了草案 §1 缺陷表的第 2 条（11% 的上下文集合抖动没有任何检索指标会
预警，证据自判是唯一能看见它的那一层）与第 5 条（§3 设计原则 2 承诺的「父块/窗口进 LLM」**从未实现**：
W2 删掉的 `parent_expand` 是个没人读的键，代码里没有任何邻居块扩展）。**代价**：若 E2 否证「多喂块有用」，
P1 里 `check_evidence` / `read_window` / 停机三块白写；子查询分解、trace 落盘、等长护栏、
parity 扩展这四件是两条路共用的，不会白。

**门槛与推进顺序（本次拍板明确接受的风险）**：E2（上下文预算消融 6→15/25 块）**没有跑**，
它仍是草案 §1 第 1 条动机（覆盖率被清单格数封顶）的 go/no-go。本期允许的推进方式是：P1 全离线先行（0 成本、不产生任何
对外质量数字），**E2 出结论前不启动 P2/P3，agent 的任何质量收益不得进 README 或 §5.3 的口径**。
表格密度普查同属 P0.5，它决定草案 §1 第 3 条（全库 179 个表格、固定 512 切下 85 个被切断或跨块、
而黄金集里表格数值题 0 条）到底能不能凑出 ≥8 条跨篇数值对比题 —— 凑不出来那条动机就是空的。

**E2 怎么跑：三条命令，不需要新代码。** 它的杠杆是 `eval --max-contexts N`；这个开关
**同时**压 `retrieval.max_contexts` 与 `rerank.top_n`，因为进 LLM 的块数是两者的 min
—— 只压一个是假杠杆，两臂其实是同一份预算（`tests/test_eval_contexts.py` 锁住了这条）。

```bash
uv run doc-rag eval --rewrite --rerank --max-contexts 6    # 臂 A：现产品口径（6 块）
uv run doc-rag eval --rewrite --rerank --max-contexts 25   # 臂 B：多喂块
uv run doc-rag compare-ragas <A 的结果文件> <B 的结果文件>  # 文件名带时间戳，CLI 会打印
```
判读只看**答案级**：`contains_acc`（must_contain 逐条命中）与分题型的要点命中；
Faithfulness 那一列会被刚补上的等长告警标成伪影 —— 这是预期的，两臂块数本来就不同，
它正是那条护栏该说话的地方。结果文件的 `meta.context_budget` 会记下两臂各自的生效预算。

**草案转入本节时的代码复核改掉了 5 处**（草案文字与仓库不符，一律以下面这版为准）：

1. 草案 §4 的「五入口一致性」**不成立**：parity helper 原名为 `_drive_all_four`，改正前覆盖 `/query`、
   `/query/stream`、演示页、eval **四条**；CLI 走同一个 `Orchestrator` 但无断言（§5.4 W1 已同步改正，
   断言本身已随 P1 补齐 —— 见本节末「P1 进度」）。
2. 答案轨护栏的缺口比草案说的小、但位置更精确：`n_contexts` **已经在** eval 的 `items[]`
   （`eval/runner.py:335`）与 summary 里，缺的只有 **RAGAS 轨的 `per_item`**（`runner.py:889-900`
   只写 `{id, type, faithfulness}`），且 `compare.py:166` 给 RAGAS 臂的是 `aux={}` →
   `_length_warnings` 在该轨恒空（`compare.py:255-281` 每条告警都要求两侧 aux 非 None）。

   而且**绝不能**按草案写 `retriever.collection = ...` —— 那正是 W1 刚拆掉的串库隐患

5. trace 现在落不了盘：`log.py:19-31` 的 `_FIELDS` 是白名单，不在表里的 `extra=` 键**静默丢弃**；
   `metrics.py` 只有进程内聚合计数（`_SAMPLES` 上限 500），无逐请求记录。逐请求 trace 必须自己选
   通道（随结果文件落盘，或独立 JSONL），并给 `JsonFormatter` 加键。

**P1 进度（2026-09-20）：parity 矩阵已补成五条入口**。`_drive_all_entries` 驱动 `/query`、

顺带一条实测发现：`answer_stream` 不接受 `plan_override` 这条不对称**今天无人使用**（eval 重放走
`answer`），所以不加投机参数；但 agent 的 trace 重放一旦要覆盖流式入口，必须先收这条。

**P1 进度（同日续）：`agent.py` 与 trace 通道已落地。** 有界状态机（步数夹在 [1,3]、token 预算
先于下一次检索生效、判定挂了退化成「停」而不是「继续查」）、`read_window`（按
`uuid5(NAMESPACE_URL, chunk_id)` 精确取邻居点，不重新 ingest、不碰 `retriever.collection`）、
`check_evidence`（走 `eval/judge.py` 的 endpoint 装配，但超时/重试按 `agent.*` 压下来）。
trace 现在真的能落盘：`Result.trace` → `/query` 响应、SSE 的 `done` 载荷、eval 结果文件的条目、
`log.py` 的 `_FIELDS`（`agent_steps` / `agent_stop_reason`）、`/metrics` 五条 agent 计数。
重放守卫照 `rewritten` 那条纪律补：带 trace 的条目若落盘上下文不是编号版就**拒绝重放**，
不退回单次检索去还原并集。默认 `agent.enabled: false`，五条入口的现行为逐字未变。

两处判断值得留痕：① 分题型开关键在**预测**题型（改写的 aggregate/year 推出来的），不是黄金集
真题型——真题型在服务侧不存在，拿它当开关会让五入口 trace 不可比；预测准不准改由
`meta.agent.type_matches_gold` 事后度量。② agent 臂的上下文预算**替换**单发口径
`min(max_contexts, rerank.top_n)`，因为砍回 6 块就砍掉了这层的理由；代价是答案轨必须先有
同块数对照臂。

**P0.5 的第②项（表格密度普查）已跑完，成本 ¥0，结论是否证**：`doc-rag census-corpus`
只读 `data/parsed`，不碰 Qdrant 也不碰 LLM（原判在 P0.5 的 ¥2~4 里，那笔钱其实全是 E2 的）。
实测 1127 篇里 **106 篇含表格、共 179 个表格**（与 §5.3 那组 179 独立对上了），
但**含数值行的只有 29 个**；把「同一行标签出现在 ≥2 篇」当作跨篇数值对比题的原料来数，
raw 13 个标签里 8 个是日期行、4 个是序号列，**剔掉之后只剩 1 个**（「入职日期」，覆盖 2 篇）。
→ **§1 第 3 条动机（表格数值题=出题+分块）在这份语料里是空的**，v3 的新题型从三类降到两类：
**时间线推翻**（普查到 14 个「同主题 ≥2 时间点」的候选，够出 ≥8 条）与**窗口依赖**。
`tables_per_doc.max=9`、45 篇有 ≥2 张表，所以「表格被切断」这件事本身仍然成立——它是
§5.1 分块的既证结论，只是**不能**再拿它当 agent 的出题动机。

**时间线题型在规则 3 不放宽下的 gold 口径（2026-09-20 定）**：gold 只取**后一次**决议，
`must_contain` 落在后来那篇的关键句，「推翻」只体现在问题的措辞里。这样它是检索挑战
（要把后一篇顶到前列，而同类文档的措辞几乎一样），合成口径逐字不动；
「A 后来推翻了 B」这种合并陈述仍然留给 P4。
（同日补充：这条口径**继续有效**，但这类题不属于 v3 multi-hop——它的 gold 只有 1 篇文档，
不满足「按构造保证单条清单必败」，归到 recency/时效那条线，见本节末 P1-g。）

**P1-e 同日完成：答案轨的等长护栏已经存在。** RAGAS 轨的 `per_item` 现在带 `n_contexts`
（`eval/runner._run_ragas`），`compare()` 的 RAGAS 臂接上了既有 aux 通路，两臂块数不等时
`compare-ragas` 会单独报「faithfulness 随上下文变长单调走高，这个差偏向块数多的一臂」——
措辞与检索轨那条（分母被长度改变）**分开**，因为后果不是一件事。旧产物没这个键时护栏
不置可否：既不假装等长，也不凭空报错。剩下的一半不是代码：P3 必须真的跑出那条
**同块数**对照臂，否则门槛 2 仍不成立。

**P1-f 同日完成：parity 矩阵补上 `mode` 这一维。** agent mode 下五条入口逐项相等的是
**trace 步数、每步 action 序列、停机原因、判定调用次数、prompt token 合计、并集文档数**。
能在 mock 下比这些的前提是注入**确定性假 judge**（脚本化判决序列，每条入口之前重置游标）
——判定本身不可复现，不脚本化就没有「相等」可言。trace 的采集点放在 `run_agent` 那一层
而不是各入口的返回值上：这样「某条入口悄悄绕过 policy 层」会直接表现为 traces 少一份
（突变验过：给 CLI 塞一个 `mode="single"` → 报 `5 != 6`）。

**P1-g（v3 出题）跑完，结论是「现有语料里挖不出来」。** `doc-rag gen-gold --v3` 实现了唯一还
站得住的新题型——**窗口依赖题**：值只在 B 块、说的是哪件事只在 A 块（同篇相邻），所以
**只装单块的清单按构造答不全**，而 `read_window` 补的正是邻居块。真实语料跑出来：候选邻块对
5 个，带决议线索词且主语不是模板词的 **3 个 → 只出到 3 条题**（判据 ≥8）。性质复检
`v3_property_violations` 随文件落盘并通过，而且它不是恒真的：把 `must_contain` 换成 A 块里
也有的词、或把 `required_chunk_ids` 换成当前分块里不存在的块，它都会报。

三类新题型的下场都由这两次 ¥0 测量定了：跨篇表格数值**被否证**；时间线推翻**不满足入场券**
（它的 gold 只有 1 篇文档，考的是 recency/排序，也就是 §1 第 4 条那条不需要 agent 的线 ——
上面定的「gold 只取后一次决议」口径仍然有效，但它属于 recency 题型，不属于 v3 multi-hop）；
窗口依赖**只有 3 条原料**。v2 里确有 19 条「gold 文档数 > 检索预算」的题（最多 56 篇：
`cross_doc` 8 + `time_filter` 11），那是并集天然能发力的题面，但它们不在新预算口径下，
按本节开头的口径规则只能并列、不能与 v3 混用。→ **v3 要成 24 条只有一条路：造料**
（扩 `scripts/make_sample_corpus.py` 生成窗口依赖形状，或走 LLM 出题 + 逐字 grounding 校验）。
在 E2 之前做这件事，等于把钱花在一个还没被证明会赢的方向上 —— 所以 P1 到此为止，
**agent 一期现在只有机制与护栏，没有可量收益的题面**。

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| 导出 PDF 的表格/标题解析质量不达标 | find_tables + 画像抽样人审；人审修复或换导出方式，不引入平台 API |
| 范围膨胀烂尾 | 严格 Phase 1 验收；GraphRAG/UI 全放 Phase 3 |
| API 费用 | 小模型起步；ingest 批处理；query 缓存 |
| 评估集太少被质疑 | 每类型至少 8–10 条；公开构造过程 |
| 抄袭感（和教程太像） | 强调：分层解析路由、消融数字、拒答策略、可复现 eval |
| 被质疑「AI 代做」 | 细粒度 commit 历史；白板讲清架构与每个取舍；消融可复现 |
| 敏感批次出域审批 | 已确认走云端 API；OpenAI 兼容 adapter 保留切内部网关的能力 |
| BGE-M3 sparse 的 API 不暴露 | 已查证（2026-09）：SiliconFlow 只返回 dense。Phase 1 直接走 Dense+BM25(jieba)；sparse 列为 Phase 2 实验（火山引擎 BGE-M3 / 本地 GPU） |
| OpenRouter 免费档仅 50 请求/天 | 实测撞限（free-models-per-day，Reset 次日 00:00 UTC）。评估循环（62 条起）用免费档跑不完 → **评估用 DeepSeek 官方（约 ¥3–5/轮）**，免费档留给交互式查询与冒烟；或充 $10 解锁 1000 请求/天 |
| 元数据抽取质量不稳 | 日期用正则 + LLM 兜底；参会人/议题抽 10–15% 人审；抽取 prompt 纳入评估 |
| 同质语料区分度低 | 元数据过滤 + Rerank；跨文档聚合题专项评估 |
| .doc 老格式转换失真 | LibreOffice headless 归一后抽 5–10% 人审；异常件单独处理 |
