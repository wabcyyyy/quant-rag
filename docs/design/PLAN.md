## 1. 项目定位

**问题**：几百份分散的会议记录里没有可靠的检索与复用路径。「关于供应商预付款，我们做过哪些决定」这类问题，全文搜索答不了，参与过会的人也记不全——而「哪一次会定了什么」正是这类语料唯一的价值所在。

**难在语料同质**：一个查询动辄命中几十份结构相似的记录，区分靠的是会议身份（日期/参会人/议题）与决议状态，而不是单纯的语义相似度。另一条硬约束是**「讨论过但未决定」不能答成已决**——由合成 prompt 的规则约束 + 专项评估题守住，不靠模型自觉。

**因此工程预算花在四处**：入库时的结构元数据抽取、Dense+BM25 混合检索 + 元数据过滤 + 重排、强制引用与无据拒答、以及自建黄金集驱动的消融评估。接入层刻意做薄（见 §2「不做的事」）。

## 2. 技术决策（已确认）

| 项 | 选择 | 理由 |
|----|------|------|
| 路线 | 自研薄编排层：重型轮子全用库，公司定制层自己写 | 不重复造轮子；贡献集中在文档特有定制，讲得清 |
| 接入 | 飞书/Word 批量导出 PDF + doc(x)，手动迁入 data/raw | 不对接平台 API；增量靠重下 + sha256 去重 |
| 文件解析 | doc/docx：LibreOffice headless + mammoth；PDF：PyMuPDF | born-digital 语料，轻依赖即可；MinerU 兜底**只是设计位**（画像把疑似扫描件标成 `scan_suspect`，但链路里没有 OCR，见 README 已知不足） |
| 元数据抽取 | LLM 入库时抽取：日期、会议类型、参会人、议题、决议 | 会议记录的检索价值一半在元数据；300 份短文档抽取成本可忽略 |
| 编排 | 自研 Pipeline（不引编排框架，模块边界清晰） | 解析/分块/评估全是深度定制，框架抽象碍事；agent 一期同样拍板自研薄循环，见 §5.5 F2 |
| 存储 | Qdrant（Dense + 全文 BM25 双路） | Query API 原生 RRF 融合；单存储，几千份规模无压力 |
| Embedding | BGE-M3 dense via SiliconFlow API | 中文文档正确默认；API 不吐 sparse（2026-09 查证），hybrid 第二路走 Qdrant full-text BM25 |
| Reranker | bge-reranker（本地小模型）或 API rerank | 性价比高 |
| LLM | DeepSeek 官方 API：`deepseek-flash`（实测选定，见「模型选型」） | 包含匹配 0.836 vs GLM-4.5-Air 0.745，价差被本地响应缓存抵消；思考型模型，合成侧延迟是主要瓶颈 |
| 评估 | RAGAS + exact-match 双轨；黄金集 v0 ≥30 → 终版 ≥50（v1 实为 63 条，题型分布见 §5.3） | LLM 打分与确定性指标互为校验 |
| 交付 | CLI + FastAPI；Gradio 演示页作加分项 | 基线优先，演示够用即可 |

**不做的事（刻意收窄，避免烂尾）**：多租户权限、生产 K8s、GraphRAG 全量、多模态 VLM 深度集成（可留作 roadmap）。

```text
│  → Rerank → top-n     │     │  doc(x) · PDF(PyMuPDF) · 手动迁入 raw     │

        │                               │

│   Qdrant（向量+全文） · SQLite/JSON 元数据 · data/raw 原文件         │
└───────────────────────────────┬─────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────┐
│  OpenAI 兼容 LLM API · BGE-M3（Dense+Sparse）· bge-reranker（本地/API）│
└─────────────────────────────────────────────────────────────────┘
```

**五条设计原则**

1. **接入克制**：born-digital 简单版面快通道已够，不为想象中的难例引重依赖——MinerU 是条件触发；语料手动迁入，不对接平台 API。  
2. **检索块 ≠ 合成块**：小块/句级召回，父块/窗口进 LLM。  
3. **默认 Hybrid**：纯 Dense 搞不定条款号、文号、专名，Dense+BM25 双路是底线。  
4. **引用可追溯**：答案 → `[1][2]` → `doc/page/block`。  
5. **评估驱动**：改任何参数先跑黄金集，拒绝「感觉变好」。

## 5. 核心实现要点

### 5.1 离线 Ingest

```text
PDF（飞书/Word 批量导出，手动迁入 raw）→ PyMuPDF：文本块 + find_tables 重建带框表格
doc/docx            → LibreOffice headless 归一 → mammoth（保留标题结构）
    → 统一中间 JSON（blocks: type/heading_level/text；PDF 附 page/bbox）
    → 结构感知分块
    → 元数据（doc 级 LLM 抽取：date/meeting_type/attendees/topics/decisions +
      chunk 级：title, section_path, page, block_type）
    → Embedding
    → Qdrant upsert + 元数据落盘
```

元数据以 LLM 抽取为主；文件名日期（会议纪要命名惯例）用正则解析作第二信号交叉校验；增量靠重下 + sha256 去重（几千份内无压力）。

**幂等与对账：两个方向都要量**

`doc_id = sha256(源文件)[:16]`（内容寻址），所以「增量」只有两种形态：新增文件、内容改过的文件——**改名不产生新 doc_id**。入库按 doc_id 删旧再插，于是有两个方向的差额：

- **正向（解析 → 入库）**：差额逐项有归属（空文档 / 解析失败 / `limit` 截断）。改造前
  1127 篇只入库 1121 篇，那 6 篇空文档在任何输出里都不存在。
- **反向（库 → 语料）**：删旧只删「本次要重插的那篇」。所以**源文件被删掉或改过内容时，
  旧 doc_id 的点永久留在库里，而且照样能被检索命中**——带的是旧日期与旧正文。改一份纪要
  = 新 doc_id，新旧两份同时在库里被召回。这比漏入库更难发现：没人会怀疑结果里有它。
  它同时是「哪一次会定了什么」这类时效/版本题的前置缺陷（旧决议被后续会议推翻时，
  被推翻的那份还在被引用）。

现在每次 ingest 结束都做反向对账：全库 scroll 一遍只取 `doc_id` payload
（3856 块 ≈ 4 次请求），报幽灵文档数与块数、「语料有库里没有」的篇数、以及 parsed_dir
里已无对应源文件的陈旧产物。`ingest --prune` **只报告**，`--prune --yes` 才删，删前三道闸：
① 有解析产物读不通 → 拒绝（那些旧点归属无法判定）；② 要删的比留下的多 → 拒绝（几乎一定是
`--kb` 或 `--parsed-dir` 串了库）；③ `--limit` 时 `keep` 判据自动从「本次源文件」退回
parsed_dir（子集不能当全集判据）。

> **✅ 已在真实库跑过（2026-09-23，升级 2026 Phase 0.3）**：全量 `ingest --raw-dir data/raw
> --prune`（只报告、未加 `--yes`）——反向对账（判据 = 1130 个源文件的 sha 集）**幽灵文档
> 0 篇 / 0 块**，语料缺口恰为已知的 6 篇空文档（+1 重复 +2 解析失败，均历来不在库里）。
> 同轮全量 re-ingest 顺带量出：**重嵌入不位级幂等**（向量带 API 浮点噪声，近并列排序会
> 位移，检索基线重发规则因此修订——见 §5.6 Phase 2.4 与 [guides/metrics.md](../guides/metrics.md) §8）。

**分块默认**

| 规则 | 值 |
|------|-----|
| 正文块 | 300–600 汉字 / ~400–800 tokens，overlap 10–15% |
| 切分依据 | 会议记录按议题/发言人段落优先；通用走标题层级 → 段落 → 滑动窗口 |
| 表格/公式 | 整块，禁止硬切 |
| 必带元数据 | `doc_id, page, section_path, block_type` |

Qdrant 侧为 `doc_id / page / block_type` 建 payload index，支撑元数据过滤与规模化检索。

### 5.2 在线 Query

```text
问题 → (可选)改写/关键词 + 实体/时间识别
     →（可选）元数据过滤（date / attendee / topic）
     → Dense top-k + BM25 top-k（Qdrant full-text，jieba 预分词）
     → RRF 融合 (k=60)
     → Rerank 取 5–8 块
     → 扩父块 / 去重
     → LLM：仅依据上下文 + 编号引用 + 不足则拒答
```

> Phase 1 正选：BM25 为 hybrid 第二路（已查证：SiliconFlow API 不返回 sparse 权重，2026-09）。learned sparse（火山引擎 BGE-M3 / 本地 GPU FlagEmbedding）列为 Phase 2 消融实验。

> 跨文档聚合题（「关于 X 我们做过哪些决定」）：检索结果按 doc_id 聚合去重后再合成，引用按文档归组。

### 5.3 评估闭环

> **指标定义与判读规则已抽到 [guides/metrics.md](../guides/metrics.md)**（每个指标怎么算、分母与
> 缺失值处理、三条噪声地板、八种常见误读）。本节及 §5.5 继续承载**结果值与放行判定**——
> 规则在那份文档里，数字在这里，两边不重复也不互相覆盖。
>
> **2026-09-21 命名标准化 + 补标准读数**（改了名字与新增列，**没有改任何已发布数字**）：
> `summary` 的键换成 IR 标准名（`mean_doc_coverage`→`recall_at_list_macro`、
> `coverage_ceiling_mean`→`recall_ceiling_macro`、`contains_acc`→`strict_keyword_accuracy`、
> `keypoint_hit_ratio`→`keypoint_recall` 等），**旧键由标准键在同一处派生写出**，所以历史工具与
> 旧命令照样可读、两个名字永远同值；`--metric` 两侧都接受。同时新增一族真读数：
> 逐条落盘 `retrieved_doc_ids`（去重保序 ranked 清单）之后，`recall_at_5`、
> `precision_at_5`、`ndcg_at_5`、`map_at_5` 才第一次可算——它们在 09-21 之前的
> 结果文件上判 `unscored`（「没测」，不是「测了且为 0」）。**标准族只用一个截断 K=5**
> （理由见 `runner._rank_metrics` 的 docstring：LLM 只读 6 块，@8 里有两三格模型没看过）。
> **为什么以前不敢叫 Recall**：这个仓库 2026-09-19 就把 `recall_at_k` 改过名成 `hit_at_k`，
> 因为当时逐条只有首命中位次、算不出真 Recall（护栏在 `tests/test_eval_metric_definitions.py`）。
> 现在两类名字并存且**必须给出不同的数**：实测同一批 20 条聚合题
> `hit_at_list = 1.0` 而 `recall_at_list = 0.1609`——相等才说明有一个是假的（已锁进测试）。
> 另注：`recall_vs_ceiling`（旧 `coverage_vs_ceiling`）是**分段**指标，
> `#清单 ≤ #gold` 时数值上等于 Precision@清单、`#gold < #清单` 时退化成召回，
> 所以它不能顶替 precision 这个名字。

**这一族自己交的两笔学费（写下来，因为都是「名字/定义」级的错）**：

1. **@10 是假数据点**：第一版扫 1/3/5/10，而清单只有 8 格 → `recall_at_10` 在
   **64/64 条上逐字等于**整条清单的召回。它看起来是一个独立测量点，其实是同一件事
   复制了一遍。→ 定死单一截断 K=5，且**k 超过清单长度的读数一律不出**。
2. **Precision 的单位错配**：第一版写的是「命中的**不同文档**数 ÷ **块**数」，
   分子按文档、分母按块，于是单文档题满分只有 1/8 = 0.125，全量读出来 0.3301
   像是很差的检索。实际它谁也没衡量——fact 类**全部命中**却只能得 0.125。
   → 改成与 recall 同用去重后的文档排名、分母 = k，`precision_at_5 = 0.3969`。
   这一条是被「为什么 precision 这么低」这句追问逼出来的，不是自己发现的。

**标准 IR 读数的第一次全量测量（2026-09-21，`results_20260921_200212.json`）**：
`eval --rewrite --rerank --retrieval-only`（72 条、清单 `fixed:8`、上下文仍 6 块、不调合成）。
它**不是新基线**——与已发布重叠的四项逐字相同：Hit@5 0.9219 · MRR 0.8242 · nDCG@8 0.8299 ·
`recall_at_list` 0.7233 · `recall_vs_ceiling` 0.8906（逐条均值，不是 0.7233/0.7917）。
新出来的 K=5 一族：**Recall@5 0.6968 · Precision@5 0.3969 · nDCG@5 0.8422 · MAP@5 0.8131**
（同一份数据用另一套离线实现算，四个数逐字相同 → 实现互相验过）。
最有讲相法的是 **`Hit@5 0.9219` 与 `Recall@5 0.6968` 差 22.5pt**——「碰到」与「捞全」的差，
正是 09-19 之前那个 `Recall@k` 名字底下藏着的量。分题型才有信息：
fact / open_discussion 的 `Precision@5 = 0.2` 是「5 格里 1 格相关」的定义值不是质量差；
**cross_doc `Precision@5 = 0.95` 而 `Recall@5 = 0.1598`**（槽位几乎没浪费，低召回是
gold 中位 37 篇造成的，所以 Recall 永远要配上限读）；真正的弱项是 **term：Hit@5 只有
0.8333**，唯一一个连「碰到」都做不全的题型。整条清单口径的缺口仍在聚合题：
cross_doc 0.2086（上限 0.2777）、time_filter 0.3020（上限 0.3708）。

**同一次运行暴露并修掉的一个读数错误**：`--retrieval-only` 下 `refusal_acc` 印 **0.0**，
而八条拒答题的 `answered_ok` 全是 `None`（压根没生成答案）——分母用了
`len(refusables)`，把「没测」印成「测了且全错」。这是本文件已经禁过两次的那类错误
（`coverage_by_type` 不给 no_answer 编 0.0、`over_refusal` 的 None 不参与），
只是它一直藏在「只有 retrieval-only 才会走到」这条路径上。已改为只数真判过的条目，
回归测试 `test_refusal_acc_is_undefined_not_zero_without_answers`（含反证：带答案跑必须给 1.0）。

**消融 #2 Faithfulness 全量复测：一次度量口径 bug 的完整复盘**

先核对口径：原记录的 0.641 / 0.821 一度被当成「15 条抽样值」（配置里 `ragas_sample: 15`），
但查 judge 缓存发现原始判分已覆盖全部 55 条可答题（112 次陈述抽取调用 ≈ 2 分支 × 55 + 重试），
**原值本就是全量**。用全量 55 条独立重跑复现，差异 ≤0.35pt：

| 分块策略 | 原记录（旧口径） | 独立重跑（旧口径） | 修正口径 |
|---------|---------------|-----------------|---------|
| 结构感知（默认） | 0.641 | 0.6375 | 0.9563 / 0.9423（两轮，均值 0.9493） |
| 固定 512 切 | 0.821 | 0.8210 | 0.9546 |
| 配对差异（固定 − 结构） | +0.180 | +0.1834（95%CI +0.070~+0.297，p=0.014） | +0.0054（95%CI −0.030~+0.041，p=0.46） |

**这 18pt 既不是抽样造成，也不是 judge 噪声**：独立重跑与原值差 ≤0.35pt；而 18pt 是噪声地板
（1.4pt，见下）的 13 倍，符号检验 p=0.014（赢/输 30/13），是个统计上稳固的差异。
但它**不是分块策略的质量差异**——追下去发现是**评估口径 bug**：

- 送 LLM 的上下文带 `[n]（文档名 第p页）` 定位前缀，而存进结果文件、再喂给 RAGAS 的
  上下文**只有正文**。合成 prompt 要求答案标注来源文档名，于是「《某文档》中…」这类
  归属陈述在 judge 眼里无据可依，整条被判为不忠实。
- 量化：结构感知分支里提及文档名的 18 条均值 **0.475**，不提的 37 条 **0.716**（24pt 全在口径上）；
  固定切分分支提及的 10 条 0.854，反而略高于不提的 0.814。
- 两个分支受罚程度不同，是因为**固定 512 切的块正文自带文档标题**（硬切不剥标题行），
  judge 能在正文里找到；结构感知把标题放进元数据（section_path），正文里没有。
  同一条答案在两个分支的「可验证性」不同——**分块策略被意外耦合进了度量口径**。
- 最典型的一条 q007：答案逐字引用上下文里的「最小规格（2核CPU，1G内存，0副本）：67元/月」，
  judge 判 0.00，理由是「上下文没有提到《高校排名网站运维服务报价单》这一文档标题」。
  **逐字引用被判成不忠实**，7 条零分里 5 条属此类。

修正：把 LLM 实际看到的上下文串（含编号与文档名前缀）原样交给 judge；上下文带 `[n]` 编号后，
答案里的引用标记也从「永远无法验证的陈述」变成可验证项。修正后 18pt 差距归零
（配对差 +0.5pt，95%CI 跨零，p=0.46），分题型差异也全部落在 5pt 内。

**judge 噪声地板（同条件全量重跑两轮，关 judge 缓存）**：0.9563 / 0.9423 →
**均值的噪声地板 = 1.4pt**；55 条里 **21 条（38%）分数会变**，多数在 ±0.06 内，少数 0.16~0.32
（如 q019 0.88→0.56）。注意：15 条子集两轮只差 0.7pt，**小样本会低估噪声**——条目级翻转
不会按 √n 均掉，噪声地板必须用与结论同规模的全量来测。
→ 修正口径下 0.5pt 的差距**小于噪声地板，判为无差异**；旧口径的 18pt 是噪声地板的 13 倍，
是稳固差异，但来源是口径 bug。

**残余噪声的机制（单条 0↔1 翻转的原因）**：抽查 q007——答案逐字引用上下文原文，
修正口径下两轮里有一轮给 1.0，单独再跑一次却给 0.00，理由是「上下文没有提到『数据库本体』」。
而「数据库本体」只出现在**问题**里，不在答案里：**陈述抽取器把问题措辞注入了陈述**，
NLI 再据此判否。这是修正口径后残留的主要噪声源。
定位手段已固化为 `doc-rag probe-judge <结果文件> <条目id>`（打印抽出的陈述 + 逐条判定 + 理由）。

**检索侧的不可复现性（附带发现）**：同配置重跑，重排 API 对近似并列项会抖动——
63 条里有 3 条（结构感知）/ 14 条（固定 512）的上下文发生变化（合成缓存命中率 95% / 78%），
包含匹配随之在 0.800~0.818 间波动。**重排不是位级可复现的**，这比 judge 温度更值得注意：
它同时污染检索指标与答案，且两次重放的块**集合**都会变（不只是顺序）。

**黄金集的合规入库（2026-09-18）**：真实黄金集（`gold.json`，v2 72 条）含公司内容不入库；
格式模板以**脱敏合成样例**入库（`data/eval/golden_sample.json`，虚构公司内容，10 条覆盖
7 题型）——「公开构造过程」由两层落地：构造脚本（`gen-gold`）+ 格式模板。字段契约见
`eval/schema.py`。同日补齐配套：10 篇合成会议纪要入库（`data/sample_raw/`，生成脚本

**机制：延迟 ≈ 输出长度 × 推理开销**。本轮 63 次合成实际消耗输入 12.6 万 / 输出 14.2 万
tokens，其中 **12.97 万是看不见的 reasoning（占输出 91%）**。聚合题要求跨 15～25 块
归纳，答案 700～900 字，思考量随之爆炸——这是 25～38s 的来源。

**low 档实测（2026-09-20）· 结论：不采纳，但理由和直觉相反。**

先做成一次**只动非聚合侧**的对照（聚合两格在档位表里不变 → 两臂聚合答案逐字相同，
这既是设计也是内部对照，实测 20/20 相同、`cross_doc`/`time_filter` 的 faithfulness
逐字相同，确认这一臂没有污染聚合侧）：

| 读数 | 现分流（非聚合=默认思考） | 非聚合改 `low` | 差 |
|---|---|---|---|
| 端到端 p50 / p95（真延迟，全部未命中） | 3874 / 17102（已发布基线） | **2993 / 13796** | −23% / −19% |
| 思考 token 占输出 | 91%（历史值） | **89%**（37,073 / 52 条 = 713/条） | 几乎没变 |
| `answered_ok`（配对 n=72） | 0.8472 | 0.8611 | +1.4pt，CI [−2.8,+5.6]，赢/输/平 2/1/69，p=1.0 |
| faithfulness（配对 n=64） | 0.9279 | 0.8884 | **−3.95pt**，CI [−9.58,+0.73]，赢/输/平 9/11/44，p=0.824 |
| └ 分题型 faithfulness | term 0.9097 · fact 1.0 · decision 0.9106 · open 0.8629 | **term 0.7292** · fact 0.9792 · decision 0.8886 · open 0.8739 | term −18.1pt，CI [−45.1,+6.3] |

三条判读：

1. **省得不多，而且没省到点上**：p50/p95 各降两成左右，但思考仍占输出的 89%——
   `low` 是个**上限**不是中间档：探针实测它只在思考量本来就大的请求上起作用
   （term 慢尾 2,029→1,195 token、10.2s→5.9s），轻项上等于不传（fact 160 vs 170、
   term 轻项 337 vs 363），而**聚合题上只砍 20% 思考（5,463→4,360、22.9s→19.5s）**
   ——所以「全局 low 取代这张表」会把聚合题从 1.7s 拉回 19.5s，直接破「聚合 ≤5s」。
2. **质量这条不能判"无损"**：`answered_ok` 完全读不出差别，faithfulness 点估计
   −3.95pt 超了 1.9pt 的 judge 地板，但配对符号检验 p=0.824、CI 跨 0；损失集中在
   term（−18.1pt，CI 宽到 [−45,+6]，n=12），5 个大动条目里 4 条向下、其中 2 条
   1.00→0.00。而本节早已记过条目级 faithfulness 不可复现（同一答案三次判
   0.167/1.0/0.167）→ **本轮既不能给 low 放行，也不能宣布它已被证明有害**。
3. **决定：不采纳，现状不动。** 理由是这轮真正的不对称——现分流的「聚合关思考」
   有大 n 的两项无损证据，`low` 只有一轮 n=64/72、CI 跨 0 的读数。要翻案需要
   扩样本 + 同配置重跑 judge 取极差，而收益只有两成延迟，不值得优先。
   档位表本身保留：它把「特例」变成了「按预测题型的策略声明」，并且**默认值不再
   依赖 `.env`**（裸检出也能拿到分流），域外键（`term: low`）直接报错而不是静默失效。

配套新增一档判读能力：`compare-retrieval --metric answered_ok` 现在可以配对判答案轨。
它**故意不叫 `contains_acc`**：summary 里那个的分母是 `scorable`（非拒答且有判据，64 条），
而这个指标能取到的最大集合是所有 `answered_ok` 非 None 的条目（含拒答题，72 条）。
差值不受影响（两臂同分母），均值不许借那个名字。

**延迟口径（与 §5.3「评估可信度口径」并列）**

- **缓存命中的耗时不是延迟**：命中时只查一次本地 sqlite（毫秒级）。测延迟必须
  `--fresh-answers`（或 `DOC_RAG_LLM_CACHE=0`）；结果文件里 `latency.cache_contaminated`
  为真就说明本轮合成延迟被低估。
- **数字必须能追到出处**：结果文件 `meta` 记录 `llm_model` 与 `answer_cache`，
  `summary.latency` 记录分阶段与分题型分位数。此前延迟数字只存在于 PLAN 文本里，
  没有脚本也没有结果文件，才导致两个数互相矛盾而无人察觉。
- **分题型报，不报单一值**：本语料延迟双峰，混合 P95 会同时低估短答案、藏起聚合题。
- **样本量决定 p95 的可信度**：n<20 时 p95 基本等于 max。`_quantiles` 用最近秩法
  （不做插值），小样本下更保守。
- **检索侧与 LLM 解耦**：检索延迟只依赖嵌入 + Qdrant + 重排，换模型不必重测。

**成本审计与优化（Phase 2，实测 token 数）**

调用量盘点（优化前）：

| 环节 | 调用量 | 单次用量 | 问题 |
|------|--------|---------|------|
| 文档元数据抽取 | **1 次/文档 = 1130 次** | ~2–3k 输入 | 最大单点；date 靠正则即可，topics/attendees 未被任何检索路径使用 |
| RAGAS judge | 25 条 × 2 指标 × 多次内部调用 ≈ 100–200 次 | 含上下文 | 第二大；AnswerRelevancy 中文噪声大（0.40 但答案明显切题） |
| 合成问答（评估） | 62 次/轮 | 普通题 2646 输入；**聚合题 6911 输入 + 1471 输出** | 7 条聚合题占整轮 25% 输入 / 48% 输出 |
| **响应缓存** | **完全没有** | — | 同批 62 条题重复跑了 6 轮（372 次调用，约 310 次是重复付费） |

已实施的四项优化：

1. **本地响应缓存**（`llm.cache`，`.cache/llm_cache.sqlite`）：键 = 模型+messages+参数哈希，
   命中即返回不发请求。实测重复评估命中率 **76%**（48/63），**同配置重跑基本零成本**；
   换模型/prompt 自然产生新键，不会误用旧答案。可用 `DOC_RAG_LLM_CACHE=0` 关闭。
2. **元数据抽取改 opt-in**（`--llm-meta`，默认关）：避免 1130 次调用的地雷。
3. **RAGAS 抽样 15 + 只留 Faithfulness**（`eval.ragas_sample` / `eval.ragas_metrics`）：
   judge 调用减少约 60%。
4. **上下文上限**（`retrieval.max_contexts: 10`）：约束输入 token；重排后通常更少。
   另删除配置里未实现的 `judge.repeat: 2`（避免配置说谎）。
5. **judge 调用量实测可见**（`_TokenCounter` 回调 + `--fresh-judge` / `--ragas-out`）：
   一轮全量判分 = 55 条 × **2 次调用** = 110 次，输入 18.7 万 / 输出 57.5 万 tokens。
   Faithfulness 每条约 2 次调用（抽陈述 + 一次**批量** NLI 判定），
   不是「每条陈述一次」——按后者估会高一个数量级。**先量再算。**
6. **逐条分数落盘**（`<结果文件>_ragas.json`，含 `per_item` / `by_type` / `token_usage`）：
   此前只打印到控制台，导致 PLAN 里的 Faithfulness 无法追溯到逐条分数，
   也就无法回答「差异是抽样、judge 噪声，还是口径 bug」——正是这次复测卡住的地方。

**成本审计第二课：账单的大头是「看不见的思考」，不是调用次数（2026-09-17 深挖）**

上面那批优化省的全是**调用次数**；把 9-17 全天账单拆开才发现方向没对准：

| 计费项 | token | 占比 |
|--------|-------|------|
| 输出（含隐藏 reasoning） | 6,259,669 | **74%** |
| 输入（未命中缓存） | 1,051,880 | 13% |
| 输入（命中缓存） | 1,099,877 | 13% |

- **deepseek-flash 是推理型模型**：judge 的输出里 **97~98% 是看不见的 reasoning token**
  （实测一次陈述抽取：可见 111 字符，计费 1,665 token，其中 1,609 是思考）。
  此前的成本审计按「可见文本长度」估输出（1471 token/条），**漏掉了 reasoning，低估一个数量级**。
- 最反直觉的结构：**「把答案拆成陈述」这个最简单的子任务最贵**（输出 1,700~1,900 token、可见仅百来字），
  是真正做判定的 NLI 步骤的 3~4 倍。
- **修复不需要换模型**：`reasoning_effort=none`（同一个 deepseek-flash、只关思考）
  → judge 输出 58.9 万 → **5.6 万 token（10.4×）**，reasoning 归零；
  Faithfulness 0.9460，落在开思考两轮（0.9563/0.9423）之间，配对差 −0.33pt（p=0.076），
  远在 1.4pt 噪声地板内。**一轮全量判分的成本从 ~¥5 降到 ~¥0.5**。

**成本护栏（配合「避免调度失误浪费」，全部有 mock 回归测试，零付费验证）**

11. **入库默认安全**：`index_parsed` 的 `use_llm_meta` 缺省改读 `metadata_extraction.enabled`

**判读工具化：`doc-rag compare-retrieval`（2026-09-19 深夜，把 RAGAS 轨那套搬到检索轨）**

2. **生产预算的 +10.92pt 覆盖率几乎全是清单变长**（8 格 → 平均 13.25 格；上限
   0.7917→0.9445）。同口径的 `coverage_vs_ceiling` 反而从 0.8906 降到 0.8723
   （cross_doc 0.8125→0.6877），点估计向下、p=0.18。→ 「上下文预算消融」的性质变了：
   它不是「检索变好了去看答案」，而是「纯粹多喂几篇文档进 prompt 值不值」，
   一个成本/噪声问题。**E2 的决策代价因此比原来估的低**（不动检索质量的任何结论）。
3. **检索轨的重跑噪声地板 = 0（doc 级）**：同配置两遍，64 条的 Hit@5/Hit@8/MRR/nDCG@8/
   覆盖率**逐条全等**（配对判读 0/0/64）。上面第 3 条那 11% 的不确定全部落在
   「哪 6 块进 LLM」这一层，且其中只有 4/72 条换了**文档**、另 4 条换的是同一篇文档的
   另一个**块**。→ 检索指标可以放心当确定性量用；答案侧的 run-to-run 差异
   **不会有任何检索指标先报警**，只能靠上下文自检（`ragas_from_results`）挡。

**拒答判分补了一条真检查：`doc-rag audit-refusals`（2026-09-19 深夜）**

在此之前拒答只有措辞口径：`_refusal_ok` 命中 12 个词之一就算「正确拒答」，而 RAGAS 轨按定义
把 `no_answer` 排除在 faithfulness 之外（正确拒答的套话按构造不可验证，见下面那条伪影）。两条
轨合起来的结果是：**8 条拒答题从没被人看过里面写了什么**。最危险的一类不是短句，而是几百字、
带 `[1][2]` 引用、还转述了实质内容的「拒答」（q069：415 字 / 7 处引用）。

现在有一个二元判定：这条拒答有没有把上下文里没记载的内容当成事实讲出来。判定读的是结果文件
里落盘的那份上下文（`[n]（文档名 第p页）` 前缀版，与 LLM 当时看到的逐字一致），**所以审计
不需要 Qdrant、不重新检索**；旧格式（只存正文）直接跳过不判——那是当年 faithfulness 被低估
32pt 的同一个 bug，别在审计里再犯一次。

实测（judge=deepseek-flash · temperature=0 · 一条一次调用）：

| 结果文件 | 拒答题数 | 编造率 |
|---|---|---|
| `results_20260919_135225.json`（v2 · 72 条） | 8 | **0.0** |
| `fenliu_on_v1.json`（v1 · 63 条） | 8 | **0.0** |

**正对照先做**：把 q069 的尾巴改成「公司已于 2026 年 3 月办公会通过每吨 120 元的碳税决议，

`why` 说上下文里没有碳税与委托征收。这条检查不是恒真，16/16 的 0.0 才有意义。judge 的 `why`
还显示它真的回核了转述内容（q067「10% 年利率、短期/长期借款划分…与 [1][2] 原文逐字一致」、
q071「薪资档次与时薪增幅能在 [1][5] 中逐字对应」）→ 这些长拒答转述的是上下文里实有其事的东西。

限制两条：① **judge 与生成同源**（都是 deepseek-flash），正对照只证明「这条检查不是恒真」，
证明不了「不是自偏」——跨供应商复判见下一块；
② 它只回答「有没有把上下文外的东西当事实讲」，**不评**「该答的有没有答」——一条把无关上下文
复述一遍的拒答在这条上拿满分，那是 answer relevancy 的地盘（已降级为诊断信号）。所以
`refusal_acc`（措辞口径）保留，两条一起看才是完整的拒答判分。

**judge 自偏：跨供应商复判（同日，`--judge-model` / `--judge-base-url`）**

`eval.judge` 现在可以指向另一家供应商（留空 = 继承生成侧 `llm`；命令行可再压一层）。
三条规则：换供应商时**丢掉归因头**，也**绝不把生成侧的 api_key 带过去**（那是另一家的凭证），
只有当 judge 端点 == embedding 端点时才复用那同账号的 key（SiliconFlow 的 embed 与 chat
共用一把，密钥少一处落地）；judge 侧固定 `reasoning_effort: none`（判定不需要思考——实测
同源那 16 条开着思考判的结果与关掉**逐条相同**，只是慢：p50 1.3s → 0.9s）。

对照 = 同一批落盘答案 + 同一份落盘上下文 + 同一个 prompt（`refusal-audit-v1`），只换判分方：

| 条目集 | deepseek-flash（同源） | Qwen3-30B-A3B-Instruct（SiliconFlow） | 逐条一致率 |
|---|---|---|---|
| v2 · 72 条那批的 8 条拒答 | 0/8 编造 | 0/8 编造 | **1.00，零翻转** |
| v1 · 63 条那批的 8 条拒答 | 0/8 编造 | 0/8 编造 | **1.00，零翻转** |
| **正对照**（往 q069 塞一句碳税决议） | 判「有编造」 | 判「有编造」 | 1.00（5 条里同为 1 条） |

正对照那一行是关键：两家独立模型都能抓住同一句注入的断言并逐字回引，所以 16/16 的
「零编造」不是两家一起放水。审计产物落盘在 `data/eval/audit_refusal_{ds,qwen}_{v1,v2}.json`
（gitignored），`--against` 可复现这份对照。

**这条验收没买下什么**：一致 ≠ 正确。两个模型共享的训练语料与偏好，可能让它们以同一种方式
宽容；跨供应商只排除了「同一家护同一家」这一种偏袒，也排除了「换个 judge 结论就翻」这一种
脆弱。

**Faithfulness 的跨供应商重判（同批答案 n=64 · 同一份落盘上下文 · 只换判分方）**

| 判分方 | Faithfulness | 说明 |
|---|---|---|
| deepseek-flash（同源，本次重判） | **0.9451** | 与在档 0.9264 是同一批答案的两次全量判分 |
| Qwen3-30B-A3B-Instruct（SiliconFlow） | **0.9700** | 跨供应商 |

配对判读（`compare-ragas`，家族=1）：**差 +2.49pt，95%CI [−0.72, +5.76]，18 涨 / 10 跌 / 36 平，
符号检验 p=0.185 → 不显著**。分题型六个方向全部 ≥0（decision +3.8pt、open_discussion +4.5pt
最大；fact 两方都是 1.00）。→ **结论：换 judge 不改变任何判断**，但点估计上外部 judge 更宽容，
所以「同源判分偏严」这个方向是存在的，只是这批数据量不到它。

**同一台 judge 自己重跑的方差比原先记的地板大**：0.9264 → 0.9451 = **+1.87pt**，全量 n=64、
temperature=0、配置逐字相同。原来的 1.4pt 地板是 v1 · n=55 那两轮测的。所以现行地板取
**≥1.9pt**（只有两次全量样本，说「不小于 1.9」而不是「等于 1.9」）。这条直接收紧两处说法：
消融 #2 的「0.5pt 无差异」仍然安全（0.5 < 1.4 < 1.9），但任何落在 1.4~1.9pt 之间的
Faithfulness 差值从此不再有结论资格。

**判分缺失必须按题型看，不能只看条数**：Qwen 第一轮 60s 超时下丢 9 条，第二轮 8 条，
其中 **6 条是 time_filter（12 条里的一半）+ 1 条 cross_doc**——正是上下文最长的那批。
缺的全是难条目，均值就被幸存者抬到 0.9726（补齐后真实值 0.9700）。修法是把
`eval.judge.timeout_s` 从 60 提到 180（8 并发下长上下文请求会排队，60s 不够）；
教训写进了配置注释：**任何 LLM 判分的缺失都要检查题型分布，非随机缺失会自己造出提升。**

另外这只覆盖拒答审计与 Faithfulness 两条；`answer_relevancy` 仍是同源单判（已降级为诊断信号，
不进质量门禁，不值得再花一轮）。

**口径改名（同日）：`_contains_loose` → `_contains_as_subsequence`**

落盘键随之改为 `answered_ok_subseq` / `contains_acc_subseq`（2026-09-19 之前的结果文件仍是
旧键名；没有代码消费它，只有人读）。理由是这路指标做的是**字符子序列**匹配——关键词的每个字
按序出现即命中，假阳性没有上界（「通过决议」能命中一句毫不相干的话，测试里锁了这个用例）。
原名听着像「容忍改写」，读数上又总与严格口径同值（本轮 0.8438 == 0.8438），等于一个看不见
自己在干什么的指标。收紧成词级匹配**没做**：在当前这批题上它与严格口径同值，也就还不知道
它想抓住什么——改名让语义可见，收紧与否留作能被讨论的决定。

**评估可信度口径（应对「RAGAS 是 LLM 打分，可信吗」）**

- **judge 的上下文必须与 LLM 实际看到的逐字一致**（含 `[n]（文档名 第p页）` 前缀）。
  这是踩过的坑：只传正文时，答案里凡提及来源文档名一律被判不忠实，两个分块分支因此产生
  18pt 的假差距（见「消融 #2 全量复测」）。**先验证度量本身，再比较数字。**
- judge 模型与版本固定，temperature=0；用 `--fresh-judge`（关 judge 缓存）+ `compare-ragas`
  实测运行间方差：同条件**全量 55 条**两轮差 1.4pt，55 条里 21 条（38%）分数会变；
  2026-09-19 又在 v2 全量 64 条上重判同一批答案，0.9264 → 0.9451 = **1.87pt** →
  **现行地板取 ≥1.9pt**（只有两次全量样本，只敢说「不小于」）。落在 1.4~1.9pt 之间的
  Faithfulness 差值从此不再有结论资格
  → **噪声地板要用与结论同规模的全量测**（15 条子集只差 0.7pt，会低估）
  → **小于噪声地板的差异不下结论**
- 抽样必须**均匀覆盖**，不能取前 N 条：黄金集按题型分块排序，`rows[:15]` 整段漏掉
  cross_doc/time_filter（同一批逐条分数换成前 15 条口径，差距会从 18pt 放大到 33pt）
- 配对判读三件事（`doc-rag compare-ragas --group 标签=文件1,文件2`）：
  ① 全量同题配对差 + 自助法 95%CI + 符号检验；② 组内重跑极差（噪声地板）；
  ③ 子集敏感性（同一批逐条分数，只换取样口径会得出什么结论）
- 只报告相对变化（before/after），不吹绝对分
- 人工抽查 15–20% 校准 judge
- 日期/数值/文号类事实题用 exact-match / 包含匹配，不依赖 judge

**黄金集构造的两次迭代（失败案例分析素材）**

- v0：跨文档题用词频选词 → 选出「处理结果/本处/case」等泛词与导出残留 token，
  来源集合无意义（Recall 0.25）。**根因是题目质量问题，不是检索问题。**
- v1：改为**结构信号抽人名**（`部门@姓名：` / 提案者 / 主持），并用 `@` 模式做交叉验证提纯
  → 18 个零噪声真人名，构造出有区分度的跨文档/时间题。零 LLM 成本（`gen-gold --programmatic-only`）。
- 同类问题：解析层碎化 PDF（每字符一行，4.5%）导致 grounding 校验 30/44 违规——修复行重建后归零。

**被推翻的结论**：重排的 MRR 增益（旧 +3.8pt）在 LLM 改写下翻成 −0.8pt，当时以为只剩
Hit@5 +3.1pt 站得住。之后同一晚又推翻两次：① 「nDCG@8 −3.4pt、文档覆盖率 −1.6pt」是
两臂清单长度不同（6 格 vs 8 格）造成的伪影，等长重测为 −0.04pt / 0；② 剩下的
Hit@5 +3.1pt 与 MRR −0.8pt 也**没有结论资格**——配对判读（`compare-retrieval`）给出
2/0/62、p=0.50 与 6/8/50、p=0.79，n=64 时 ≤2 题的差不可能显著。
**现行结论：等长口径下重排对检索指标无可测影响**，详见 §5.3「判读工具化」。
**回答质量表已按新口径全量重跑**（2026-09-19 · 72 条 · LLM 改写 + 重排 + 收紧 prompt ·
冷缓存 · 144 次真实调用 + judge 128 次）：包含匹配 0.875→**0.8438**（−3.1pt ≈ 2 题，
未归因，检索侧同条件 Hit@5 都是 0.922 所以不像改写造成）、拒答 1.00、引用有效 1.00、
引用存在率 1.00→**0.9583**（缺的 3 条全是拒答题，拒答天然不带 `[n]`；剔掉拒答 69/69=1.00）、
RAGAS Faithfulness **0.9264**（n=64 全量 judge、关缓存；与旧 0.95 不同黄金集版本，不可直接比）、
端到端 p50 3.9s / p95 17.1s，超 8s 的条目 33%→**15.3%**。详见 README「回答质量」。
测试从 111 项增至 206 项，仍全离线、`pytest` 21s 内跑完、零 API 成本；
CI 四道闸门：ruff check / ruff format --check / mypy（渐进式基线，见 pyproject 的
`tool.mypy.overrides`，只能缩短）/ pytest。

**重跑时顺手挖出的两个度量口径缺陷**（都不是模型问题，是指标自己说谎）：

1. `over_refusal_rate` 恒真：定义是「答案出现拒答措辞 且 上下文含关键信息」，而收紧后的
   prompt **要求**模型说明「文档里没记载什么」。本轮被标记的 26 条**全部**答对了
   must_contain → 0.406 是 100% 假阳性。已收紧为「且答案确实没交付关键信息」（本轮按新
   定义 = 0.0），两种情形各一条回归测试。一个恒真的指标比一个偏高的更糟——它会把人
   引去修一个不存在的问题。
2. Faithfulness 条目级不可复现：q014 存 0.00 → 复判 0.50，q003 存 0.43 → 复判 1.00，
   q029（15 条臂）同一答案三次判 0.167/1.0/0.167。机制是枚举答案被拆成排他单句、
   正确拒答与 hedge 的套话按构造不可验证。§5.3 的 1.4pt 地板是 **n=55 均值**尺度的数，
   条目级幅度大一个数量级 → 结论：Faithfulness 只能用于同规模配对比与大样本均值。

**上面第 2 条的机制展开（15 条臂的 q029 / q063 · `probe-judge`）**：n=14 里两条离群值吃掉
0.092 缺口的 90%（q029 0.167 = 0.0595、q063 0.667 = 0.0238），两条都是度量侧：

- **枚举答案的块级翻转**（q029）：答案把五门课逐字列全并引用，上下文原文就是这五门；
  RAGAS 拆成 5 条「五门课程是《X》」的单门陈述后，判定阶段按排他读 → 5 条一起判否。
  **同一份答案、temperature=0、关缓存连判三次 = 0.167 / 1.0 / 0.167**，且 5 条同涨同落
  （一次批量调用决定整组，翻转相关而非逐条独立）。同题在 09-17 那轮（n=55）判 1.0。
- **拒答套话按构造不可验证**（q063，一条**正确**拒答）：两句实质陈述都判 ✓，
  唯一判 ✗ 的是「根据现有文档无法回答该问题」——它断言的是问答情形，不是文档内容。
  注意判分集合只排除 `type==no_answer`，`time_filter`/`fact` 上的正确拒答仍进集合并被扣。

不绕过：改 RAGAS 的拆句/判定提示词等于换度量身份，宁可把结论限制在配对差 + 大样本上。

### 5.5 Agentic RAG 升级（2026-09-20 拍板 · 方案与自评记录在 `docs/design/AGENTIC_RAG.md`）

一句话：在 `orchestrator` 之上加一层 **policy**（有界多步检索 + 证据自判），不引编排框架、
不做多轮会话、不动 §5.3 已经确立的单发基线口径。

下文「草案」= `docs/design/AGENTIC_RAG.md`，其 §N 编号是该文件内的编号。
**刻意不做**（草案 §2 的边界，一并搬过来）：不接外部工具与互联网、不做自由 tool 选择的
autonomous agent、不做多租户/权限、GraphRAG 全量仍留 Phase 3；**步数上限 ≤3**，单请求的
token 与延迟预算硬封顶。

**三条分叉的结论**

| 分叉 | 拍板 | 已接受的代价 | 重开条件 |
|---|---|---|---|
| F1 合成规则 3（禁止把多篇信息合并成任何单篇都不存在的陈述） | P1~P3 **一字不放宽**，「放宽」做成 P4 独立臂 | 第一版看起来「不够 agentic」，更像会自己多查几次的检索器，答案仍是逐篇事实的枚举 | 只由 P3 结论推动 |
| F2 循环自研 vs LangGraph / LlamaIndex workflows | **自研薄循环**（有界步数 + 显式状态 + trace 落盘），≈600 行 | 停机/重试/超时自己写；框架在 policy 与预算这两处本来就帮不上忙 | — |
| F3 多轮会话状态 | **本期不做**，agent 限定在「单条问题内的多步」 | 产品上少一个「追问」；换来不动服务契约（服务端状态要连鉴权、限流、缓存键、「同一句第二次问算不算同一测量」一起重做） | 独立一期 |

F1 的代价比草案写的**高一档**：草案把「放宽规则 3」和「agent 送了更多块进 LLM」混成一件事。
即使规则 3 一字不动，只要 agent 臂的 `contexts` 比单发臂多，faithfulness 就天然偏高。
**保住可比性的不是「不放宽」，而是答案轨的等长护栏** —— 它当时不存在，2026-09-20 已落地
（见本节末 P1-e；缺的一半是 P3 要真跑出一条同块数对照臂）。

**F2 的前置问题：为什么不是「确定性子查询分解器」**（草案 §9 第 5 条自己提出的更窄方案，不回答就不能定架构）

分解器与 agent 押的是同一条动机（§5.3：覆盖率被清单格数封顶 —— 8 格 0.7233 / 上限 0.7917，
生产预算 25 下 0.8325 / 上限 0.9445，而同口径 `coverage_vs_ceiling` 0.8906→0.8723，即变长
≠ 变准），成本与延迟确实更可预测，也**同样**需要 trace 与等长护栏。选 agent 的理由只有一条：
**分解器是 agent 的一个消融臂，反过来不成立。** 分解器 = 固定一步扇出、无证据自判、无停机决策；
agent 减去 `check_evidence` 再减去 `read_window` 就退化成它。所以做完 agent 能一次回答「收益
来自哪一步」，先做分解器则永远回答不了草案 §1 缺陷表的第 2 条（11% 的上下文集合抖动没有任何检索指标会
预警，证据自判是唯一能看见它的那一层）与第 5 条（§3 设计原则 2 承诺的「父块/窗口进 LLM」**从未实现**：
W2 删掉的 `parent_expand` 是个没人读的键，代码里没有任何邻居块扩展）。**代价**：若 E2 否证「多喂块有用」，
P1 里 `check_evidence` / `read_window` / 停机三块白写；子查询分解、trace 落盘、等长护栏、
parity 扩展这四件是两条路共用的，不会白。

**门槛与推进顺序（本次拍板明确接受的风险）**：E2（上下文预算消融 6→15/25 块）**没有跑**，
它仍是草案 §1 第 1 条动机（覆盖率被清单格数封顶）的 go/no-go。本期允许的推进方式是：P1 全离线先行（0 成本、不产生任何
对外质量数字），**E2 出结论前不启动 P2/P3，agent 的任何质量收益不得进 README 或 §5.3 的口径**。
表格密度普查同属 P0.5，它决定草案 §1 第 3 条（全库 179 个表格、固定 512 切下 85 个被切断或跨块、
而黄金集里表格数值题 0 条）到底能不能凑出 ≥8 条跨篇数值对比题 —— 凑不出来那条动机就是空的。

**E2 怎么跑：三条命令，不需要新代码。** 它的杠杆是 `eval --max-contexts N`；这个开关
**同时**压 `retrieval.max_contexts` 与 `rerank.top_n`，因为进 LLM 的块数是两者的 min
—— 只压一个是假杠杆，两臂其实是同一份预算（`tests/test_eval_contexts.py` 锁住了这条）。

```bash
uv run doc-rag eval --rewrite --rerank --max-contexts 6    # 臂 A：现产品口径（6 块）
uv run doc-rag eval --rewrite --rerank --max-contexts 25   # 臂 B：多喂块
uv run doc-rag compare-ragas <A 的结果文件> <B 的结果文件>  # 文件名带时间戳，CLI 会打印
uv run doc-rag compare-retrieval --group 臂A=<A文件> --group 臂B=<B文件> \
    --metric keypoint_hit_ratio                             # E2 的主读数
```
判读只看**答案级**，而这里原先有一句过时的话：它写着「`contains_acc`（must_contain
逐条命中）与分题型的要点命中」，可 gold v2 的 20 条聚合题**每条只有 1 个 must_contain**
（就是那个人名），而答案集 10~56 篇——「答出 2 篇」与「答出 18 篇」在 contains_acc 上
同分，两臂必然都是 1.0。所以 E2 的 arm 判据换成了真正分档的那一个：

- **主指标 `keypoint_hit_ratio`**（`eval/runner.py`，逐篇要点命中数 / K）：聚合题的每条
  gold 文档贡献一个**全库唯一、且除名字之外真的主张了件事**的逐字短语
  （`goldgen._key_points`，零 LLM）。它是纯字符串判据，**不依赖清单/上下文块数**，
  所以两臂块数不等时它是唯一不用先扣除长度伪影的答案级读数——`compare-retrieval`
  把它标成 `answer` 轨（噪声标签与告警口径都分开），块数不等**不再**触发等长告警，
  而两臂 K 不同才触发（那才是分母变了）。
- `contains_acc` 降级为次要读数（对聚合题它只回答「提没提到那个人」）。
- Faithfulness 那一列会被刚补上的等长告警标成伪影 —— 这是预期的，两臂块数本来就不同，
  它正是那条护栏该说话的地方。结果文件的 `meta.context_budget` 会记下两臂各自的生效预算。

**判据覆盖率是量出来的一件事，不是假设**：真实语料重生成后 20 条聚合题里 **17 条**
拿得到要点（`meta.aggregation_key_points` 随文件自证），K 为 1~7、均值 3.88；
3 条 K=0（q046/q049/q063，那三个人的出现几乎全是纯 `@` 提及，挑不出既含实体又
唯一还主张了件事的句子）。K=0 的条目该指标判 **None 不进分母**，所以 E2 的答案级
配对是在 17 条上做的——报结论时必须带上这个 n。

**E2 跑完了（2026-09-20）· 结论：多喂块买到了答案质量，但买不起延迟；且「纯上下文消融」在这条链路上不是良定义的操作。**

三臂（同一份 gold v2、同 `--rewrite --rerank`，逐条判据为 A 阶段修好反斜杠后的版本）：

| 臂 | 检索清单 | 进 LLM 块数 | `keypoint_hit_ratio`（macro, n=17） | 可答上限（micro，原句进上下文） | 逐字命中（micro） | 捕获率 |
|---|---|---|---|---|---|---|
| A 现产品口径 | 固定 top-8 | 6 | **0.1951** | 25.8% | 16.7% | 64.7% |
| B 只动 `--max-contexts 25` | 固定 top-8 | **被截在 8** | 0.1676 | 28.8% | 15.2% | 52.6% |
| C 同时 `--top-n 25` | top-25 | 25 | **0.4623** | 53.0% | 37.9% | **71.4%** |

- **A → C 是本轮唯一有效的那个对照**：同题配对差 **+26.7pt**，95%CI [+10.9, +42.7]，
  赢/输/平 10/2/5，符号检验 p=0.0386（Holm 家族 = 1）。分题型：cross_doc 0.111→0.367
  （n=6）、time_filter 0.241→0.515（n=11）。三值分档 full/half/zero 从 1/7/9 变 5/6/6。
- **这条提升不是「格子数」伪影**：与检索轨那次相反（`coverage_vs_ceiling` 0.8906→0.8723，
  涨的是清单长度），这里**捕获率也升**了（64.7% → 71.4%）——多进来的文档被真的用进了
  答案，不只是分母变大。
- **B 臂解释了为什么「纯上下文消融」不成立**：`context_budget` 落盘是
  `{max_contexts:25, rerank_top_n:25}`，而 `n_retrieved` 只有 8 —— **清单比预算短，
  预算就被截住**。喂不进没检回来的文档，所以只动 `--max-contexts` 最多只能从 6 块到
  8 块，而 2 块的变化没有可测效应（−2.75pt，CI [−11.8, +3.5]，p=1.0）。
  → **E2 的正确形态是「检索预算 + 上下文预算」的合并臂**，这一点写进结论而不是留在踩坑记录里。
- **代价（决定它不进默认口径）**：C 臂 72 次真调用、输入 489,776 / 输出 70,547 tokens
  ≈ **6,803 输入 token/条**，是 A 臂未命中条目（~1,980/条）的 **3.4 倍**。答案长度
  同步翻倍（与缓存无关，可直接配对比）：cross_doc 570.8 → 981.8 字，time_filter
  668.8 → 1452.3 字。C 臂本轮合成**全部未命中**（`cache_contaminated: false`），
  所以它的延迟是真数：cross_doc 端到端 p50 3535 / p95 8642.7ms，time_filter
  p50 4885.6 / **p95 12551.9ms** → 对照 README 里「聚合 ≤5s」的现基线（cross_doc
  p95 3.7s / time_filter 6.2s）是**明显恶化**。⚠ 与 A 臂的延迟差**不可读**（A 被缓存
  污染，`cache_contaminated: true`、45 条命中），要拿延迟差必须 `--fresh-answers` 再跑一轮 A。
- **所以放行判定是「有条件 go」**：答案质量方向成立，但把默认口径从 6 块推到 25 块会
  同时作废 README 头条质量基线与聚合 SLO，本轮**不改 `configs/default.yaml`**。
  C 臂的正确用途是**P3 那条「同块数对照臂」**——§5.5 门槛 2 要求 agent 臂必须有
  single-shot @25 块的对照才准进答案轨结论，这份文件现在已经在库里
  （`results_20260920_210500_kc.json`）。
- 顺带用生产数据钉死了 A 阶段的动机：`contains_acc` 在这 17 条聚合题上**三臂恒为 1.0**
  （饱和），而 `keypoint_hit_ratio` 读得出 26.7pt 的差与逐条方向。
- **口径缺口（2026-09-21：①② 已各自量到底，剩 ③ 与下面那条延迟没闭合）**：① 判据是逐字命中，**冤枉率已全量核对（2026-09-20，取代此前
  「最长公共子串归因 + 没有全量人工核对」那半句）**：三臂各 66 条要点逐条走四级放松阶梯
  （L1 去标点并大小写归一 → L2 再去数字 → L3 再去主语人名），能翻绿的只有
  **A 臂 2 条 / B 臂 4 条 / C 臂 1 条**，逐条回答案原文复核过，成因只有三个：
  要点原句带着源文档的列表编号（`2\.1@康少云汇报公司章程修改情况`，模型复述内容但不复述编号）；
  主谓之间被插入动词（原文「@康少云公司章程和股权激励协议书」→ 答案「康少云**负责**公司章程和…」）；
  人名与它的一条主张被并列项目符号隔开（答案写成「张果」「讲述周会方法论」「讲述静舒说的内部沟通问题」两项）。
  **分母必须同时给两个，否则这个数字会说谎**：按全 66 条要点算冤枉占 1.5%~6.1%，
  对 macro 的影响是 A **+2.94pt**、C **+1.18pt**；按「上限内未命中」算才是 A 2/6、B 4/9、C 1/10
  （33% / 44% / 10%），后者看着吓人只因为那个池子本身有 6~10 条。
  → **对 E2 的影响：宽松口径下 A→C 配对差 +26.7pt → +25.0pt**，方向与量级都不动，
  所以那 26.7pt 不是判据伪影。但绝对值仍只配横向比臂，不配当「答对了多少」的读数。
  上限内**真漏** A 4 条 / C 9 条（C 的上限内未命中 90% 是真没抄出来）——这才是该指标要读的量。
  **本轮不改生产判据**：救回的条目里两条源于 `goldgen` 把带列表编号的句子选成了要点，
  修它要重生成 gold ⇒ 整份 66 条要点集变动 ⇒ 三臂数字全部重发（离线重判 ¥0，但要重读一遍结论），
  而它不改任何决策 —— 记在「下次因别的理由重生成 gold 时顺手做」，不要为它单开一轮；
  ② 本指标的同配置**重跑噪声地板已实测（2026-09-21，94,734 输入 / 17,222 输出 tokens、80 次真调用）**：
  同一份 20 题聚合子集、同配置（清单 8 / 上下文 6、`--rewrite --rerank`）、`--fresh-answers` 关缓存连跑两遍
  → macro `keypoint_hit_ratio` = **0.1726 / 0.2035，极差 3.10pt**；两遍的均值对现基线 A6（0.1951）的
  同题配对差 **−0.71pt**，CI [−3.68, +1.76]，逐条赢/输/平 **2/2/13**（17 条里只有 4 条分值动过）。
  两遍**输入 token 逐字相同**（47,367 = 47,367）而输出不同 → 抖动的唯一来源是生成，判据本身确定。
  **地板的用法**：本指标上小于 ~3pt 的差不得下结论。E2 的 +26.7pt 是它的 **8.6 倍**、CI 下界 +10.9pt
  也在地板之上 → p=0.0386 那条现在有了第二个支撑（原先只压在 CI 下界上）。
  反向用途同样重要：P2 的 AGENT − A6 = −2.75pt **落在地板内** → 那不是一个「变差」的读数，
  而是「与现基线不可区分」，agent 臂的问题在成本（2.2 倍）与失败分类（13/20 白付一次判定），不在质量；
  ③ n=17 条题 / 66 条要点，功效有限。

   而直喂 12 块的 S12 得 1.00**：多步并集挑进来的不是该答的那几块。
3. **机制层根因（可修，但不在本轮）**：`judge_contexts: 6` 让判定只看池子前 **6** 块，
   而合成吃 8~12 块 —— **它在批准自己没看过的内容**；且 `SYSTEM_EVIDENCE` 的判据是
   「够不够逐句回答这条问题」，对答案集 10~56 篇的聚合题这句话没有定义（任何 6 块都够回答某件事）。
   两条指向同一个修法：**判定的输入必须等于合成的输入，且「够」要对答案集规模判而不是对问题措辞判**。
   退化方向也同向偏保守（判定挂了按「够」停），所以现状下这层机制的默认行为就是**不变**。
4. **风险 1（agent 把「检索不到」伪装成「文档没记载」）在这条开关下测不到**：两臂
   `audit-refusals` 都是「0 条拒答题有答案 → 判了 0 条」，因为 `agent.types` 只在
   cross_doc/time_filter 上开，`no_answer` 题型根本不进这层。所以这条风险**既没被证实也没被排除**，
   它是被开关**结构性排除**的 —— 写结论时别说成「已审计通过」。

**P2 首跑撞到一个从未执行过的代码路径（已修）**：`read_window` 调的是
`client.get(collection=, points=)`，而 **qdrant-client 1.19.1 没有 `get`**（按 id 取点的入口是
`retrieve(collection_name=, ids=)`）→ 真库上第一次执行到 `read_window` 就 `AttributeError`。
根因不是笔误而是**测试的形状**：`FakeClient` 照着 `get` 写了一个方法，替身测试全绿而链路从未通过。
已改 `agent.py:298`，并把「替身的接口面 ⊆ 真客户端、且参数名对得上」本身加成断言
（`tests/test_agent.py::test_fake_client_only_implements_real_methods`，顺带断言
`not hasattr(QdrantClient, "get")`）。真库正对照验过：70 块的文档取第 5 块邻居返回 `:4`/`:6` 两块，
单块文档返回 0 块（这是对的，不是失败）。

**检索侧延迟读数本轮不可用，且这不是 agent 的问题**：两臂端到端 max 63,380 / 66,058ms 全落在
`retrieve` 分项（62.4s / 62.8s），而 `rerank` 232~330ms、合成 2.4~2.9s。同一条抖动在 E2 已发布的

**任何端到端 p95 读数必须先对 `retrieve` 分项**，README 那张分题型 SLO 表因此只在 p50 那一层有意义。

   这条保留判据在两遍读数下无法与噪声区分**（配对符号检验在本库现状下功效不足）；
3. q020（动议区）不在本修复可达范围（chunker 级，需重分块，显式不做）。

选项：**A. 不修**——记诊断收档，term 停留在 0.8333，等下次因别的理由重嵌入时顺手做
（判据功效问题依旧存在，须先压住检索噪声）；**B. 修**——接受 ±2 条噪声下的弱判读
（q019 的词面翻绿是确定性词法匹配、方向可预期，但「不倒退」只能报两遍极差不报显著性）。

**拍板（2026-09-23，用户选 A）：不修，诊断收档。** term 停留在 Hit@5 0.8333；「可修模式
已诊断（title 并入 BM25 文本）+ 修复判据在本库现状下无功效」一并收档，重开条件 = 检索
重跑噪声先被治理（重嵌入策略/判读协议），届时顺手实施。q020（chunker 级）维持显式不做。
