# 升级为 Agentic RAG：方案（决策优先）

> 状态：**草案**。§0 三条分叉拍板后才展开成分期任务与 PLAN §5.5。
> 口径分工（延续 A1）：本文只写工程决策、预算与验收；岗位叙事不进仓库文档。

## 0. 三条先要定的分叉

### F1 agent 循环节不节「跨文档合并陈述」——这条决定其它一切

`SYSTEM_ANSWER` 规则 3 现在明写：**禁止把多篇文档的信息合并成一个在任何单篇文档中都不存在的陈述**。

- 不放宽：agent 只做「多次检索 + 证据并集」，答案仍是逐篇事实的枚举。Faithfulness 基线（0.9451）、
  拒答审计（16/16 零编造）、噪声地板（≥1.9pt）全部继续有效。
- 放宽：能做真正的多跳（对比、时间线上的推翻）。但**这是换度量身份**——Faithfulness 基线作废，
  `audit-refusals` 的判据（「上下文里有没有逐字记载」）会把合并陈述一律判成编造，那条 prompt 得重写。

**推荐**：P1~P3 一律不放宽，把「放宽规则 3」做成 P4 的独立臂。
**代价**：第一版看起来「不够 agentic」——它更像会自己多查几次的检索器。
**收益**：能给出一个实测答案：多跳合并的收益，到底值不值得换掉整个忠实度口径。

### F2 循环自研还是引框架（LangGraph / LlamaIndex workflows）

**推荐自研薄循环**（有界步数 + 显式状态 + trace 落盘）。PLAN §2 早就把「未来多轮/agent 场景可局部引入」
记成逃生门，而本仓库的 thesis 是「重型轮子用库、定制层自研」——agent 的定制层恰好是 policy 与预算，
框架在这两处帮不上忙，反而把评测所有权让出去。
**代价**：约 600 行自研代码，停机/重试/超时都得自己写。

### F3 要不要多轮会话状态

现在整个 API 是**故意无状态**的，`test_orchestrator_parity` 还专门断言 `kb` 不残留到下一个请求
（改造前端点用 `retriever.collection = body.kb` 改的是 `lru_cache` 单例，并发会串库）。引入会话 =
引入服务端状态 → 鉴权、限流（现在是进程内单桶，多 worker 会翻倍）、缓存键、以及「同一句话第二次
问算不算同一测量」全部要重做。

**推荐**：本期不做，agent 限定在「单条问题内的多步」。
**代价**：产品上少一个「追问」。**收益**：不动服务契约，不新压一个 D 组级别的工程债。

## 2. 边界（刻意不做）

不接外部工具与互联网；不做自由 tool 选择的 autonomous agent；不做多租户/权限；GraphRAG 全量仍是
Phase 3。步数上限 ≤3，单请求 token 与延迟预算硬封顶（§4）。

## 3. 架构：policy 层，不是新检索栈

新增 `src/doc_rag/agent.py`。工具全部是现有部件的薄封装：

| 工具 | 实现 | 新增成本 |
|---|---|---|
| `search(sub_query, filters, budget)` | `HybridRetriever.retrieve` | 0 |
| `rerank(query, chunks)` | `Reranker` | 0 |
| `read_window(doc_id, chunk, span)` | 按邻居块取上下文 | **零前置成本**（本计划初稿说需要补 payload 字段，是错的）：`chunk_id` 本来就是 `doc_id:序号`（`chunker.py:69` 的 `f"{doc_id}:{len(chunks)+1}"`），邻居块 = 推出相邻序号 → `uuid5(chunk_id)` 得 point-id → `client.get(points=[...])` 精确取点。不重新 ingest、不 backfill、不建索引 |
| `check_evidence(question, contexts)` | 二元判定「证据够不够答」 | 新 prompt，复用 `eval/judge.py` 那个 endpoint 与拒答审计的解析形状 |

停机条件（写死）：证据足够 / 步数用完 / 预算用完 / 检索为空。

`Result` 只扩展不替换，新增 `trace`：

```text
trace = {
  steps: [{n, action, args, n_retrieved, new_doc_ids_added, decision, ms, tokens}],
  sub_queries: [...], stop_reason: str, budget_used: {calls, prompt_tokens, ms},
}
```

**每一轮 agent 请求都必须落 trace，judge 重放只读 trace**——沿用 `plan_override` 那条纪律：
不可复现的中间产物不落盘，就拒绝重放（改写侧已经是这么修的）。

### 默认只对两类题型开启

检索侧现在 p50 1350ms（改写 821 + 检索 232 + 重排 257），端到端 p50 3.9s / p95 17.1s。
每多一步 ≈ +1 次判定调用（~0.9s）+ 1 次检索/重排（~0.5s）+ 更长 prompt。所以 agent **按题型开关**，
默认只开 `cross_doc` 与 `time_filter`（它们既是覆盖率封顶的两类，也已有 ≤5s 的聚合 SLO 档）。
分题型开关是本期唯一的成本控制面，必须是配置而不是代码常量。

## 4. 五入口一致性：扩展 parity 测试，不是绕开它

`test_orchestrator_parity` 断言 CLI / `/query` / `/query/stream` / 演示页 / eval 五条入口送进 LLM 的
prompt 逐字相同、重排调用次数相同、上下文块数相同。agent 必须扩这条：

1. 带 `mode`（single / agent）参数，parity 矩阵在两个 mode 下各跑一遍；
2. agent mode 追加断言：**trace 步数、每步 action 集合、LLM 调用次数、token 合计**五入口逐项相等。

这是 W1 那类漂移（「文档里的头条数字描述的是一条没有交付入口在跑的管线」）目前唯一的防线。

## 5. 评估怎么才算数

新黄金集 **v3 multi-hop**（~24 条，独立文件，不与现有 72 条混），**按构造保证单条清单必败**：
gold 文档数 > 检索预算，或答案需要两篇各记载一半。三个新题型正好吃掉 §1 的三个缺口：
**时间线推翻** / **跨篇表格数值** / **窗口依赖**。零 LLM 构造优先（`gen-gold --programmatic-only` 那套）。

对照臂（同题、同 judge、同预算，只换 policy）：

| 臂 | 作用 |
|---|---|
| single-shot（现产品路径） | 配对基线 |
| agent-3step | 推荐实现 |
| agent −`read_window` / −`check_evidence` | 消融：收益是不是白来的 |

判读全部走 `compare-retrieval` / `compare-ragas`（同题配对差 + 自助法 95%CI + 符号检验 + Holm），
Faithfulness 按 **≥1.9pt** 地板判，检索指标必须过**两臂清单等长**护栏——那条护栏刚救过一次
（重排的「−3.4pt 代价」就是不等长清单造出来的伪影）。

两个必须新报的维度：**成本-质量前沿**（每题 token / p50、p95、步数分布）与**失败分类**
（用完步数仍拒答 vs 单发会答对却被答错）。没有前沿图，「agentic」就是玄学。

**验收门槛**（达标才叫升级，2026-09-20 评审后重写）：
1. **主指标是答案级**，不是检索级。多步并集下「这份清单的上限是多少」没有唯一定义（每步各自有
   上限，并集的 ceiling 怎么算取决于去重规则），所以 `coverage_vs_ceiling` 在 agent 臂上不可计算。
   v3 用答案要点命中数（`must_contain` 的逐条命中）与二值「答全/答半」作主指标。
2. **答案轨要先加等长护栏**：`compare-ragas` 目前对 faithfulness 的上下文块数**完全无感**——
   ragas 产物的 `per_item` 只有 `{id, type, faithfulness}`（实测 `ragas_ds_v2full.json`），
   而 `compare()` 的 RAGAS 路径 `aux={}`，`_length_warnings` 恒空。agent 臂必然送更多块，
   而 faithfulness 随上下文变长单调走高 → **这个比较从构造上就偏 agent**，且偏差量级正好在
   judge 自身方差（1.9pt）那一档。先落 `n_contexts` 进 `per_item`，再要求「同块数」对照臂。
3. Faithfulness 下降不超过 1.9pt，**且第 2 条的等长臂必须先存在**——否则该条不成立。
4. 聚合题 p95 不超过现有 5s SLO 的两倍；预算按 **token** 封顶而不只是步数（见 §7 风险 2）。

**基线口径**：v3 与 agent 臂的数字与现有 72 条基线**不同黄金集版本、不同 prompt 版本、不同 policy**，
只并列不比较；README 头条仍是单发路径。这就是「新旧基线口径不混用」在本期的落法。

## 7. 风险与对策

1. **agent 把「检索不到」伪装成「文档没记载」** → 拒答率虚高，而 `refusal_acc` 只查措辞看不见。
   对策：P2/P3 各跑一次 `audit-refusals`，与单发比编造率和两条过度拒答口径。
2. **延迟失控**（步数 × 思考尾部）。对策：分题型开关 + 每步自己的 `timeout_s/max_attempts`
   ——沿用改写侧那条教训：可退化的步骤不该有 12 分钟的等待能力。
3. **非确定性放大**（改写已不可复现，agent 每步都是模型决策）。对策：trace 全落盘、judge 只重放、
   P3 里同臂跑两遍并报运行间方差。
4. **成本单点转移**：`--llm-meta`（1130 次调用）现在是最大成本单点，agent 会把它挤到第二位。

## 8. E2 是本计划的 go/no-go，不是「建议先做」

§1 第 1 条动机（覆盖率被清单格数封顶）恰恰是**最容易反过来说事**的一条：8 格里已经装了捕获率 89%
的 gold，扩到 25 格后捕获率反而降到 87%——这组数字同样支持「多给槽位收益递减，agent 多查几次也
拿不到新东西」。E2（上下文预算消融，6→15/25 块）一晚上就能测完，而且现在已知它**不动检索质量结论**
（代价远低于最初估计）。所以正确顺序是：**先跑 E2**。
  · E2 显示「多喂块 → 答案要点命中上升」→ agent 的存在理由成立，本计划继续；
  · E2 显示「多喂块 → 答案不动或变差（噪声/长度惩罚）」→ **本计划应当废弃**，把预算花在
    §1 第 3/4/5 条上，那三条都不需要 agent。
B1 两路索引文本对称化、D1 真库幽灵块清理同样会改动 agent 臂的分母，但它们不是门槛。

**已改正**

   更多、每条更容易找到依据）。所以「不放宽就能保住基线」这句**不成立**，能保住可比性的是答案轨的
   等长护栏，而那个护栏目前不存在（§5 第 2 条）。→ F1 仍是真分叉，但它的代价被我低估了一档。
4. **§5 的检索级验收门槛在 agent 臂上不可计算**（多步并集没有唯一的 ceiling 定义）。已重写为答案级主指标。
5. **最强的一条反对意见，原文没有正面回答**：§1 列的 5 个缺口里，第 3 条（表格数值题=出题+分块）、
   第 4 条（时效/版本=recency 项+幽灵块）、第 5 条（窗口扩展=一个非 agent 的检索后处理）
   **都不需要 agent**；只有第 1、2 条需要，而第 1 条正是 E2 一晚上就能否证的那条（§8）。
   所以本计划的真实处境是：agent 只解决五个缺口中的两个，其中一个的成立还押在未测的 E2 上。
   被这个论证直接推出的**更窄替代方案**值得先否决掉再谈架构：
   「不要 policy 层，只给 `cross_doc`/`time_filter` 做一个确定性的子查询分解器（问题→N 个子查询→并集）」——
   没有循环、没有自判、没有步数决策，也就没有 F1/F2/F3 三条分叉，延迟与成本可预测。

6. §4 的 parity 扩展在 mock 下不可实现，除非注入**确定性假 judge**（脚本化判决序列），否则五入口的
   trace 步数根本不可比。改写侧已有「调用即炸」的桩可以先例照抄，原文没写这条。
