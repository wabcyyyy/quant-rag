# RGB 基准（AAAI 2024 中文子集）：可被独立复核的一组读数

> 为什么有这份文档：本仓库其余所有已发布数字都测在**公司语料**上，而语料与结果文件
> 按合规全部 gitignore 了——**读者无法独立复核任何一个数**。RGB 是公开可 clone 的
> 数据集，在它上面跑一遍，就得到一组「别人能自己跑出来、并与论文基线并排」的数字。
> 它替代不了「有真实用户」，但它把「数字不可验证」这一条堵上了。

## 1. 基准与协议

**RGB**（*Benchmarking Large Language Models in Retrieval-Augmented Generation*，
AAAI 2024，arXiv 2309.01431）的四类能力恰好压在本项目的强项上：
negative rejection ↔ 拒答、information integration ↔ 跨文档聚合、
noise robustness ↔ 混合检索抗干扰、counterfactual ↔ 拒答审计里的正对照。

| 项 | 值 |
|---|---|
| 上游 | `https://github.com/chen700564/RGB` |
| commit | `65ec39e40e7dc9abb50e9bf1b4f32be3f6f16615`（2024-05-17） |
| 许可 | **CC BY-NC-SA 4.0（非商用）**——所以**数据副本不入库**，仓库里只有抓取脚本与这个 commit |
| 中文四个文件 | `zh.json`(300) · `zh_refine.json`(300) · `zh_int.json`(100) · `zh_fact.json`(100) |
| 每题文档数 | 5（官方默认 `passage_num`） |
| 噪声档位 | `zh`/`zh_refine` 扫 0/0.2/0.4/0.6/0.8，另加 **1.0** 作拒答档；`zh_int` 扫 0/0.2/0.4；`zh_fact` 只 0.0 |

**关键协议事实**：RGB 是**给定文档**的基准——文档由数据集提供，**检索层不参与**。
所以主口径测的是**合成 + 拒答层**（论文基线也是这么跑的），它不测本项目的检索与重排。
`zh_refine` 是 `zh.json` 的**精修版**（作者修掉了错误的正面/噪声文档），与 `zh` 是
同一个任务；论文表格里的基线对应的是精修**之前**的 `zh.json`。
拒答的跑法是 `noise_rate=1`：**一条正面文档都不给**，模型应当拒答。

## 2. 复现

```bash
uv run doc-rag bench-rgb-fetch                      # 抓四个文件 + 写 MANIFEST（commit/许可/sha256/行数）
uv run doc-rag bench-rgb-run --sample 50 --workers 4 --yes   # 每组合均匀抽 50 条
uv run doc-rag bench-rgb-score data/eval/rgb_production_sample50_*.jsonl --judge
```

- **需要自带 LLM key**（生成侧与判分侧）。本轮 800 次调用的实测用量：
  输入 769,897 / 输出 528,354 token（其中思考 467,214），另加 149 次判分调用。
- `--sample N` 是**固定种子的均匀抽样**，不是取前 N 条；抽出来的是全量的子集，
  所以之后 `--resume` 补到全量**不会重复付费**。
- 抽到全量：`uv run doc-rag bench-rgb-run --yes --resume <上面那份 .jsonl>`。

## 3. 结果（`--sample 50`，每档 n=50，800 条 · 0 失败）

配置自证：`deepseek-flash` · temperature 0.0 · prompt 指纹 `0aaa9d262c09`（与 PLAN 里
记录的生产 prompt 指纹一致）· 生产思考档分流 · 0 条调用失败。

### 3.1 噪声鲁棒性（accuracy，越高越好）

| 噪声率 | `zh` | `zh_refine` | 论文 ChatGPT-zh | 论文 Qwen-7B-Chat-zh |
|---|---|---|---|---|
| 0.0 | **100.00%** | **100.00%** | 95.67% | 94.00% |
| 0.2 | **100.00%** | **100.00%** | 94.67% | 92.33% |
| 0.4 | **98.00%** | **100.00%** | 91.00% | 88.00% |
| 0.6 | **96.00%** | **100.00%** | 87.67% | 84.33% |
| 0.8 | **98.00%** | **100.00%** | 70.67% | 68.67% |

读法：本系统的曲线**几乎是平的**（噪声从 0 加到 0.8 只掉 2pt），而论文最强的基线
掉 25pt。生产 prompt 里那条「上下文相互矛盾时分别陈述」在这里起了作用。

### 3.2 负向拒答（`noise_rate=1`，越高越好）

| 数据集 | 官方关键词口径 | 严格口径 | 本 prompt 措辞 | **Rej\\*** | 论文 ChatGPT-zh | 论文 Qwen-7B-Chat-zh |
|---|---|---|---|---|---|---|
| `zh` | 2.00% | 0.00% | 70.00% | **82.00%** | 5.33 / **43.33** | 8.67 / 25.33 |
| `zh_refine` | 0.00% | 0.00% | 92.00% | **96.00%** | 5.33 / **43.33** | 8.67 / 25.33 |

**这一列必须按 Rej\* 读，不能按关键词口径读。** 官方判据是关键词「信息不足」，
而生产 prompt 要求回答「根据现有文档无法回答」——**措辞不同，官方关键词判据必然
判不出来**（2.00% / 0.00% 就是这么来的，它衡量的是措辞差异，不是拒答能力）。
按**语义**判读（Rej\*，judge）本系统是 82% / 96%，论文中文侧最好的是 ChatGPT 的 43.33%。

### 3.3 信息整合（accuracy，越高越好）

| 噪声率 | 本系统 | 论文 ChatGPT-zh | 论文 Qwen-7B-Chat-zh |
|---|---|---|---|
| 0.0 | **82.00%** | 63.00% | 67.00% |
| 0.2 | **80.00%** | 58.00% | 56.00% |
| 0.4 | **72.00%** | 47.00% | 55.00% |

读法：比最强基线高 15~25pt，而且**随噪声下降更慢**（-10pt vs 基线的 -16~-20pt）。
这一族要求把**两组文档**的信息整合进一个答案，两个子答案缺一不可。

### 3.4 反事实鲁棒性

| 指标 | 本系统 | 论文 ChatGPT-zh |
|---|---|---|
| **ACC**（喂被篡改的文档时仍答对） | 10.00%（**且这 10% 全是假阳性，见下**） | 91.00% |
| ED（打出「事实性错误」标记） | 0.00% | 1.00% |
| **ED\\***（judge 判「识别出了错误」） | **62.00%** | 3.00% |
| CR（识别出错误的人里答对的占比） | 0.00% | 33.33% |

**这是本轮最重要的发现，而且它是一条设计取舍而不是 bug：**

- 官方判据是子串匹配，而这一族的假答案常常**包含**真答案（实例如 `'70'` ⊂ `'170'`）。
  本系统判为「正确」的 5 条，**5 条全部同时命中了 fakeanswer**——即它答的是被篡改的
  那个值。**真实 ACC ≈ 0%**。
- 原因写在生产 prompt 的第 3 条：**禁止推断、补全、概括**，不得把上下文没有写出的
  内容写成结论。RGB 的反事实任务要求的恰恰相反——它期望模型**用参数记忆覆盖文档**
  里被篡改的事实。所以「只依据文档作答」的系统在这一族上必然接近 0 分，而一个无据
  的 LLM 能拿 91 分，代价是它在别的地方会编。
- 但 **ED\\* 有 62%**：本系统确实**察觉到了矛盾**并按 prompt 第 6 条「分别陈述」
  （实例：*「关于张继科的项目存在相互矛盾的表述，分别陈述如下…」*）。也就是说
  **它识别得出不一致，但拒绝越权改正**——这正是 ED\* 高、ACC 低的由来。
- **本轮不为刷分改 prompt**：改 prompt 就等于换度量身份，这条取舍如实报出来。

## 4. 检索变体：让系统自己检索（**这一节才测到本项目的 RAG**）

上面 §3 走的是 RGB 官方协议：**文档由数据集提供**，检索层不参与。所以那份读数只反映
prompt 与模型选型——本项目的分块、Dense+BM25 混合、RRF 融合、重排、上下文预算
**一分都没体现**。这一节把文档并成一份语料灌进 Qdrant，让系统自己去找。

```bash
uv run doc-rag bench-rgb-prepare --dataset zh        # 语料 + 同格式黄金集
uv run doc-rag ingest --parsed-dir data/bench/rgb/parsed_zh --kb rgb_zh --recreate --index-only
uv run doc-rag eval --kb rgb_zh --gold data/bench/rgb/gold_zh_retrieval.json \
                    --rewrite --rerank --fresh-answers --max-contexts 5
```

**语料**：`zh` 的 300 题涉及 11,512 个文档槽位 → 去重后 **10,883 篇**（内容寻址
`sha256(正文)[:16]`，与 ingest 的约定一致），入库 **10,891 块**，反向对账 10,883 = 10,883
（零幽灵）。**黄金集的 `source_doc_ids` 直接取 RGB 的 `positive`**——来源集合是数据集
自己标的，不是我猜的。

**判据等价性（这是两行数字能直接对比的前提）**：`eval/runner.py:349` 的规则是
`all(must_contain 都在答案里)`，与 RGB 官方 `checkanswer` 的「全部 ground-truth 元素命中」
是**同一条规则**。所以把 RGB 的 `answer` 逐项填进 `must_contain` 之后：

    本仓库的 strict_keyword_accuracy  ≡  RGB 的 all_rate

**不是换了一套指标，是同一个判据在两条路径上跑**——于是两行之差就是**检索层的贡献**。

### 4.1 同题对照（同为 300 题，同为 5 块/篇上下文）

| 臂 | 文档来源 | 准确率（≡ `all_rate`） |
|---|---|---|
| **给定文档**（数据集给 5 篇正确文档） | oracle | **99.33%** |
| **自己检索**（从 10,883 篇里检索 5 块） | 本系统 | **90.67%** |

**Δ = −8.66pt 是这轮对照的合并差**（oracle 臂拿数据集真标签选思考档、受测臂靠改写器
预测，差异含题型路由误差——见 §5.4 第 4 条；≈0.33pt 上界，反事实未跑），不能读成
「纯净的检索层上界」。

### 4.2 检索侧指标（300 题，生产配置：清单 8 格 → 上下文 5 块）

| 指标 | 值 | 读法 |
|---|---|---|
| **Hit@5 / @8** | **0.9567 / 0.9633** | 95.7% 的题，gold 来源文档进了前 5 |
| **MRR** | **0.8400** | 首个命中的位置通常在 ~1.2 位 |
| nDCG@5 / @8 | 0.7068 / 0.6626 | |
| Recall@5 / Precision@5 | 0.3721 / 0.6453 | Recall 低是因为每题 gold 是段落并集、实测 **1~33 篇**，清单只 8 格（早先写「6~19 篇」不准，2026-09-26 实测更正） |
| **Recall@清单 macro** | **0.4607**（上限 0.7523 · 归一 **0.6388**） | 「找全没有」——**必须连上限一起读** |
| MAP@5 | 0.6217 | |

### 4.3 那 8.66pt 花在哪（拆解）

- **约 4.3pt 是「根本没找到」**：Hit@5 = 0.9567，即 4.3% 的题 gold 文档不在前 5，
  这几题的上限就已经不是 100% 了。
- **约 4pt 是「找到了但没找全 / 被噪声干扰」**：`Recall@清单` 归一后只有 0.6388——
  每题 gold 是段落并集（实测 1~33 篇），8 格清单装不下，模型只能答出检索到的那几篇。
  这与本仓库在公司语料上「聚合类题目的弱项是找不全」的方向**一致**；但 gold 宽松
  同时意味着 Hit@5 偏高、4.3pt 低估真漏检。

### 4.4 这一节的数字不能与论文并排

论文没有「自己检索」这个设置，所以 90.67% **不能**与 ChatGPT 的 95.67% 比大小。
它只能与**同一份数据、同一批题**的「给定文档」那一行自比（上表）——而那个对比恰好
比跨模型比大小有信息量：它量的是**你自己的检索层**。

### 4.5 聚合题族（`zh_int`）：预算放宽的收益最大——但「聚合族」标签 ≠ 这条臂真的走了聚合路

`zh_int` 100 题，同样做了同题对照（语料 5,177 篇去重、入库 5,176 篇/5,179 块）：

| 臂 | 清单 / 上下文预算 | 准确率 | 端到端 p50 | 输入 token |
|---|---|---|---|---|
| 给定文档 | 数据集给 5 篇 | **83.00%** | — | — |
| 自己检索 | 8 格 → **5 块**（生产配置） | **47.00%** | 7.4s | 137,598 |
| 自己检索 | 8 格 → 8 块 | **53.00%** | ~8.0s | — |
| 自己检索 | **25 格 → 25 块** | **81.00%** | **10.1s** | 394,539 |

生产预算下这条臂掉 36pt，把清单与上下文一起放宽到 25 格后 **47% → 81%**。预算效应
方向为真，但两个旧说法已撤回（2026-09-26 审查 N4/N19）：

- **路由**：这些臂里改写器只有 **12/100** 的题真正走了聚合路（`meta.retrieval` 无
  `+aggregate`，路由纯来自改写器预测；分层读数：被路由进聚合路的 12 条反而更差
  0.333 vs 0.489）。「聚合族」是数据集任务标签，**不是这条臂实际跑出来的路由**——
  88% 的题走的是普通 single 路（池 8、无去重）。
- **gold 口径**：每题 gold 是两组 positive 的**全部段落并集**，实测 **4~41 篇**
  （mean 15.48；早先写「6~19 篇」不准确）。所以「Hit@5 全程 0.92」是宽松 gold 上的
  上界，`Recall@清单` 0.2687 的分母也被并集口径放大。

指标把机制说得很清楚：

| 指标 | 8 格 → 5 块 | 25 格 → 25 块 |
|---|---|---|
| Hit@5 | 0.92 | 0.89 |
| Recall@清单 macro（归一） | 0.2687（0.4626） | **0.6072（0.6214）** |
| **过度拒答（gold 已进上下文）** | **0.32** | **0.10** |
| 严格关键词准确率 | 0.47 | **0.81** |
| 端到端 p50 / p95 | 7.4s / 21.3s | 10.1s / **24.3s** |
| 输入 token | 137,598 | 394,539（**2.9×**） |

- 8 格那一臂的 **过度拒答 0.32** 是要害：聚合题要求**两个子答案都在**，检索只给到
  一半来源时，模型要么答一半（判错）、要么按 prompt 拒答（也判错）——**两种都错**。
- **这与本仓库在公司语料上的 E2 消融方向一致**（那边 +26.7pt、代价 3.4 倍输入与
  p95 翻倍，因此没有采纳为默认口径）。~~同一结论在第二份完全独立的语料与数据集上
  重现~~（2026-09-26 撤回：既然 88% 的题没走聚合路，这条对照量的是「放宽预算对
  混合路由臂的作用」，不是「聚合路在生产预算下的表现」——后者需要
  `--force-aggregate` 对照，未跑）。
- 代价也一样：**p50 7.4s → 10.1s、p95 21.3s → 24.3s，SLO 破了**。所以这不改变
  「默认口径不动」的既有拍板；它改变的是**这条取舍现在有了外部基准上的证据**。

**⚠ 一个方法学坑（实测踩到）**：我先用 `--max-contexts 25` 想喂 25 块，结果只喂进
**8 块**——因为检索清单本身只有 8 格，**上下文预算被清单长度截住了**。这正是本仓库
在 E2 消融里记录过的那条教训（「只动块数预算是半个杠杆，清单不放宽就被截住」），
在外部基准上**原样重现**。上表第 4 行才是真正的「放宽」臂（`--top-n 25 --max-contexts 25`）。

## 5. 已知偏差与不确定项（读上面的数字前必须知道）

1. **抽样**：本轮每档 n=50（均匀抽样、固定种子），论文是 300。n=50 时准确率的
   95% 区间约 ±14pt——**足以分辨论文那种 20~40pt 的差异，不足以分辨 5pt 级差异**。
2. **模型代际不同**：论文基线是 2023–2024 年的模型（ChatGPT-3.5、Qwen-7B-Chat 等），
   我们是 2026 年的推理模型，temperature 与思考档也不同。**这不是模型对比**，
   并排展示是为了让读数可解释（知道 0 分和 100 分各长什么样）。
3. **星号口径的 judge 不同源**：官方用 `gpt-3.5-turbo`，我们用本仓库 `eval.judge`
   的配置（默认与生成同源）。所以 Rej\* / ED\* 与论文的星号列**不可严格对比**，
   只能同口径自比。
4. **预测题型的来源**：给定上下文的入口不经过改写，拿不到改写计划，所以思考档按
   **数据集自带的任务标签**填（`zh_int` → 聚合档，其余 → 全局档）。生产里这个标签
   来自改写器，这是一处**声明过的偏差**。
5. **未跑官方 instruction 那一行**：`--instruction rgb` 可以跑「官方模板 + 本仓库 LLM」
   的锚点行，用来分清分数里哪部分来自 LLM、哪部分来自管线；本轮没跑（省一次全量成本）。
6. **未实现的论文列**：Table 7 的 `ACC_doc`（正文没写清定义，不猜）；
   Table 2/4/6 的英文侧与检索命中率类列。
7. **官方发布版的 `--factchecking` 路径是坏的**：`evalue.py` 会去读
   `config/instruction_fact.yaml`，而该文件**不在仓库里**（`git ls-files config/` 只有
   `instruction.yaml`）。反事实族因此只能用默认 instruction。
8. **行尾符**：`bench-rgb-fetch` 从 raw 地址取到的是上游的 LF 版本；用 `git clone`
   拿到的是被本地 `core.autocrlf` 转成 CRLF 的版本（每行多 1 字节）。两者内容等价，
   但 sha256 不同——MANIFEST 记的是 raw 版本的哈希。

## 6. 成本与时长（实测）

**给定文档那一行（§3）**

| 项 | 实测 |
|---|---|
| 调用数 | 800（16 个组合 × 50 条）+ 149 次判分 |
| 每条 | 962 输入 / 660 输出 token（其中思考 584） |
| 合计 | 输入 769,897 / 输出 528,354 token（思考 467,214） |
| 时长 | 4 并发下实测 **12.4 分钟**（逐条墙钟合计 45 分钟，并发把它压到 1/4） |
| 失败 | 0 条 |

**检索变体（§4）**

| 项 | 实测 |
|---|---|
| 建库 | 10,883 篇 → 10,891 块，**约 48 分钟**（嵌入 API 串行） |
| 评测（300 题） | 600 次调用（300 改写 + 300 合成），输入 411,199 / 输出 287,315 token（思考 249,893） |
| 评测时长 | **约 32 分钟**（`eval` 是串行的，没有并发开关） |
| 延迟 | 检索侧 p50 1.2s / 合成 p50 2.6s / 端到端 p50 4.0s；**p95 15.4s 超 8s 目标**，max 168.7s（一次端点停顿） |

**两条踩过的坑**

1. **n=2 的外推不可信**：用 `--limit 2` 的小样估出「每条 924 入 / 1227 出、10s/条」，
   把实际值高估了约 3 倍——那 2 条里有一条挂起了 20 分钟、另一条用了 5,170 个思考
   token。真正可信的是 `--sample 50` 那一档的实测。
2. **建库与评测不能并行**：两者都打嵌入端点（评测要嵌入查询），并发跑会让端点
   掐连接（`SSL: UNEXPECTED_EOF_WHILE_READING`）。而 `eval` **没有逐条容错**——
   一次抖动毁掉整轮 300 题。串行跑就没问题（本轮 600 次调用 0 失败）。
   `bench-rgb-run` 那条路径已有逐条容错 + 断点续跑，`eval` 还没有。

**一条已诊断、未实施的优化**：`embedder.embed` 的批处理只在**单篇文档内部**生效，
而这份语料每篇只有 1 个块 → 10,883 次**单条**嵌入调用（约 3.8 次/秒）。把
`index_parsed` 的逐篇循环并发化（照 `_META_WORKERS=8` 的先例）能把 48 分钟压到约
6 分钟，但那要动公司语料的入库路径，收益不值这个风险——按本仓库「诊断收档」的做法
记在这里。

## 7. 已知局限

- **检索变体不能与论文并排**：论文没有「自己检索」这个设置。§4 的数字只能与同一份
  数据、同一批题的「给定文档」那一行自比。
- **中文四个文件共 800 条**，规模远小于公司语料上的 72 条黄金集 × 1121 篇语料。
  它证明的是「换一份公开语料、同一套管线仍然工作」，不是「系统在所有中文语料上都好」。
- **拒答那一族没有检索版本**：语料里明明有答案文档，「该拒答」就无从构造
  （官方的 `noise_rate=1` 是靠「一篇正面文档都不给」造出来的）。所以 §4 只覆盖
  噪声鲁棒与信息整合两族。
- **`zh_int` 语料少 1 篇**：入库 5,176/5,177，那 1 篇是嵌入时的网络超时
  （`WinError 10060`）。**对账把这件事报出来了**（「语料有、库里没有：1 篇」），
  没有静默丢掉。若它恰好是某题的来源文档，那道题会变得不可答——影响面 1/5,177，
  但读数时要知道这个缺口存在。
- **`zh` 那一轮有 1 条改写退化**（`[口径混合] 1 条改写退化`）：那 1 条没走改写，
  所以严格说不是纯条件。项目对这种情况的处置是**报出来**而不是抹平。
- **反事实那一族的低分是设计取舍**，不是能力缺陷；但它在真实场景里值不值得改
  （要不要允许系统质疑文档）是一个产品决策，本轮没有做。
